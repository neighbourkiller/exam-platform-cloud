## 四、领取策略实现要点（§2 落地）

四阶段领取（READ_COMMITTED 短事务，`L=min(batchSize,workerCount)`，全部 SQL 侧过滤 + `FOR UPDATE SKIP LOCKED`）：

1. 全局恢复过期租约（不取模，`lease_until,id` 排序，≤L）；
2. 本片到期 PENDING（多分片时预留 `ceil(R/2)` 给跨片，其余本片领取；额度为零不发 SQL）；
3. 跨片 PENDING 补领（`available_at <= 数据库当前时间 - crossShardDelayMs`，`mod(id,total)<>shardIndex`）；
4. 本片补足（绑定参数 NOT IN 排除已选 ID；阶段 2 零配额且阶段 3 无候选时同样执行）。

单实例跳过跨片；候选 ID 唯一且 ≤L；重试任务以有效 `available_at`（含 next_retry_at）参与等待与补领。
观测：`claim_own_pending` / `claim_cross_pending` / `claim_lease_recovered_own` / `claim_lease_recovered_cross`
按成功领取计数；轮次汇总日志含分片参数与四类领取量、完成量。无 HTTP/Feign/消息/Schema 变更，无新迁移。

### 5.1 接管机制证据（本轮核心）

- 变体 12（在途 8 任务被遗弃）：`[EVIDENCE] 收敛发生时执行器注册仍为 4（未因摘除改变分片），跨片恢复为接管机制`；

- 注册表时间线（每 2 秒）与运行时事件日志（`shardTotal=4` 恒定 + `crossPending>0`）均已封存于结果目录。

### 5.2 失败轮次的证据分析（不掩盖）

- **#14 带客户端接管**：k6 阈值真实越限（k6-stdout 末行 `thresholds ... have been crossed`，客户端
  p99=55.54s）+ DB P99 47.85s。请求零失败（34,468 次全部成功），失败纯为延迟维度：客户端观察 =
  DB 完成 + 轮询间隔（约 8–10s）+ 抖动。DB 侧：接管本身 44.3s（#12），叠加 10,000 VU 轮询负载后
  P99 增加 ~3.5s。**下一步独立建议**（本轮未改动任何参数）：若需在该复合场景达标，可评估降低单次
  最终化成本或增加每实例工作线程，须单独压测验证。
- **#17 MySQL 中断 + status_first**：DB P99 56.94s（max 57.19s 仍在 60s 内，60s 窗口 100% 完成）。
  20 秒中断窗口完全覆盖 due 时刻，恢复后全部任务从 PENDING 起跑；status_first 的首轮状态探测与
  抖动等待将有效处理起点进一步后移。同窗口下 status_only 41.73s、submit 33.26s 通过——差异来自
  客户端流程而非服务端。
- 执行过程事件：第 17 轮首次执行因宿主磁盘满失败，清理构建缓存与隔离项目数据卷（严格限定项目名）
  后重跑成功；变体 13 曾因宿主休眠产生一次被污染的运行，已封存丢弃（目录带 SUSPENDED-DISCARDED
  后缀）并重跑。

### 5.3 注入条件未满足（按计划不判通过）
