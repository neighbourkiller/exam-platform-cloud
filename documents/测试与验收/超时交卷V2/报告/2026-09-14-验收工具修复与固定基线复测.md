## 三、验收工具整改与验证

### 3.1 已落地的工具行为

- 资源、注册表、Prometheus、k6 分别维护 PID、开始/就绪/停止状态；使用独立进程组，清理时逐个停止并 `wait`。
- k6 使用本轮唯一容器名和 cidfile，套件等待 k6 完成后保存真实退出码；Docker CLI 退出不再被当作 k6 已完成。
- k6 显式使用 `--summary-trend-stats="avg,min,med,max,p(90),p(95),p(99)"`，解析器对缺失、非法和非有限 P99 返回错误，不以 0 代替。
- 门禁分别判断数据库、客户端、故障注入有效性和采样完整性，生成每轮 `gate-result.json`；纯后台轮客户端状态为 `NOT_RUN`。
- 30/60 秒完成数按 `completed_at <= due_at + 30s/60s` 计算，墙钟完成数只作为诊断值保存。
- 清理流程可重复执行，不使用宽泛的 `pkill`；结果目录执行敏感数据扫描并记录 `secret-scan=CLEAN`。

## 六、故障时间线与失败解释边界

### 6.1 4→3 接管

三个接管目录均记录了目标实例 `runtime-service-4` 在杀前存在 worker 活跃数 8 和 PROCESSING 任务，且存活实例未预先暂停：

| 轮次 | 杀前 PROCESSING | 杀前 worker.active | 30s 窗口完成 | 60s 窗口完成 | `recovered_inflight_tasks` |
|---|---:|---:|---:|---:|---:|
| G1-R2 | 31 | 8.0 | 9994 | 10000 | 0 |
| G2-R2 | 24 | 8.0 | 10000 | 10000 | 0 |
| G3-R2 | 15 | 8.0 | 7825 | 10000 | 0 |

三轮 `registry-timeline.tsv` 都是 85 个有效记录，注册实例数始终为 4；故障后没有观察到注册表先变为 3 的条件。任务最终均在 60 秒窗口内完成，但指定的被杀在途任务集合没有以 `attempt_count>1` 且 DONE 的形式被计入恢复。因此本报告只写“在途租约恢复未证明”，不写“已证明跨片接管”、不写“接管失败由注册摘除/轮询/连接池中的某一项导致”。

### 6.2 MySQL 中断加 `deadline_status_first`

G2-R4 的数据库 P99/max 为 39.328/40.221s，数据库 60 秒窗口完成 10000/10000；k6 原始摘要明确显示客户端 P99 46.371s、max 50.572s，stderr 记录阈值越限，真实 k6 退出码为 99。门禁因此只将客户端组件和整体判为 FAIL，未把数据库组件误判为 FAIL。

该事实可以支持“本轮复合场景未满足客户端 45 秒 P99”，不能单独支持任何性能归因。资源、锁等待和客户端请求阶段是并行证据，后续优化前仍需做因果对齐。

12 轮的采样状态均为 `PASS`，全部记录 `no-residual-processes=PASS` 和 `files-stable=PASS`，且每轮所需的门禁、k6、数据库、Prometheus、注册表和容器资源文件均存在。

resource/registry 的瞬时错误被保留在每轮 `sampling-state.json` 中，没有被 PID 为空掩盖；Prometheus 每轮均实际观测到 Hikari、JVM 和超时任务积压指标。当前 evidence 的“采样通过”不等于采样过程中零错误。

### 7.2 观测到的运行范围

从 12 轮 `runtime-prometheus-samples.log` 和容器资源曲线汇总得到的观测范围如下：

- Hikari：活跃连接峰值 21，等待连接峰值 181，空闲连接峰值 24。
- JVM：单个 Runtime 实例采样到的 G1 heap 使用量峰值约 469 MiB。
- 超时积压：各轮从 PENDING=10000 开始；Prometheus 观测到的最大 PROCESSING 值为 24，最大 oldest-overdue 约 37.373s。
- 容器资源曲线（同一宿主机）：MySQL 观测 CPU 峰值约 208%，单个 Runtime 观测 CPU 峰值约 423%，MySQL 内存峰值约 2.26 GiB，单个 Runtime 内存峰值约 1.24 GiB。CPU 百分比受多核统计影响。

这些是同主机固定复测的观测值，不是生产容量上限，也不足以单独证明任何瓶颈。

### 7.3 MySQL 状态与 digest

每轮都保存了 `resource-summary.txt` 和 `mysql-top-statements.tsv`。跨连续隔离轮的末次 MySQL 状态快照范围为：

- `Max_used_connections`：92–125；`Threads_connected`：79–121；`Threads_running`：2–3。
- `Innodb_row_lock_waits`：1800–6810；`Innodb_row_lock_time_avg`：1–48ms；`Innodb_row_lock_time_max`：133–50901ms。
- 12/12 的 digest 文件均出现超时任务领取查询、`FOR UPDATE SKIP LOCKED`、最终载荷写入、SubmissionAccepted Outbox 写入和带令牌的任务状态更新。

由于这些 MySQL 状态值是在同一个串行隔离数据库上连续采集的，不能把累计值当作每轮独立峰值，也不能仅凭 digest 出现次数断定性能根因。
