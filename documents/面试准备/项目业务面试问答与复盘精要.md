## 领域一：答题快照与版本控制（Redis 快照 vs MySQL 权威边界）

### 问题 1.1：写 Redis 失败时的可靠性边界与自动交卷容灾
* **面试官提问**：
  > 假设第 11 版答题快照已经成功写入了 MySQL，但随后写 Redis 这一步失败了（如网络闪烁或宕机）：
  > 1. 快照保存接口应该向前端返回成功还是失败？
  > 2. 考试到期后，系统自动交卷会不会丢失第 11 版答案？为什么？
  > 3. 架构上如何界定权威数据源（Source of Truth）与缓存的关系？

* **我的实答**：
  > 接口会返回成功，自动交卷也不会丢失第 11 版答案。  
  > 因为当前方案把 MySQL 持久草稿作为可靠性边界。服务端先在本地事务中校验会话、租约和版本，再将第 11 版答案的压缩载荷、客户端序号、服务端版本和 SHA-256 摘要写入 MySQL。只有 MySQL 事务提交成功，才认为快照保存成功。  
  > 后续写 Redis 只是缓存同步。如果 Redis 不可用，服务端会记录异常，但不会推翻已经提交的 MySQL 事务，因此仍然向客户端返回第 11 版已保存。  
  > 考试到期后，超时交卷会优先根据 submissionId 读取 MySQL 中的持久草稿，并校验编码格式和 SHA-256，然后生成最终答案。所以即使 Redis 一直没有第 11 版，自动交卷仍会使用 MySQL 中的第 11 版。  
  > 反过来，如果 MySQL 事务失败，即使 Redis 写入成功，也不能向客户端确认保存，因为 Redis 不是当前流程的最终可靠性边界。

* **面试官点评与得分**：**9.5 / 10（满分级）**
  * **得分点**：结论先行，权威边界明确，异常捕获与事务隔离逻辑严密，反向论证（“MySQL 失败即使 Redis 成功也不认”）体现出极强的数据一致性素养。
  * **代码映射**：[`ExamSnapshotService.java:52-77`](../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/ExamSnapshotService.java#L52-L77)、[`SnapshotDraftPayloadService.java:96-127`](../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/SnapshotDraftPayloadService.java#L96-L127)。

* **推荐口述定稿（10 分）**：
  > “接口向客户端返回成功，且到期交卷绝对不会丢失第 11 版答案。
  >
  > 核心原因在于本系统的可靠性权威边界（Source of Truth）完全建立在 MySQL 之上。快照保存时，系统先在本地事务中校验会话合法性与客户端租约，并将第 11 版的 GZIP 压缩载荷、单调版本号以及 SHA-256 摘要写入 `submission_draft_payload` 表。只要本地事务成功提交，数据落库的可靠性契约即已达成。
  > 
  > 随后写 Redis 只是尽力而为（Best-effort）的缓存加速。若 Redis 发生瞬时异常，代码捕获 `DataAccessException` 并记录警告日志，绝不会反向推翻已提交的 MySQL 事务，更不会向客户端抛错引发恐慌重试。
  > 
  > 超时交卷时，系统优先根据 `submission_id` 读取 MySQL 持久草稿并校验完整性，即使 Redis 中只有旧快照甚至 Redis 宕机，交卷使用的依然是 MySQL 中的最新第 11 版。同时，考生按 F5 刷新页面时也是优先读 MySQL 持久草稿，因此全链路数据完全闭环一致。”

* **可能的高频追问**：
  1. *追问*：如果客户端连续快速提交第 10 版和第 11 版，网络乱序导致第 11 版先到、第 10 版后到，系统如何避免旧版覆盖新版？
     * *应对思路*：客户端每次自增 `clientSequence` 并携带 `baseServerRevision`，服务端做原子 CAS：序号小于已存序号直接拒收；序号相同摘要相同判为幂等；基础版本不匹配判定分支冲突。
  2. *追问*：为什么最终交卷读取草稿时要强校验 SHA-256 摘要？
     * *应对思路*：防止大文本压缩载荷在网络传输、磁盘存储或反序列化时发生静默数据损坏（Bit Rot），确保评分服务拿到的是完整不可变的答案载荷。

### 问题 1.2：高并发答题场景下的防风暴设计（架构权衡）
* **面试官提问**：
  > 既然系统读取与最终交卷都以 MySQL 为权威源，那么：
  > 1. 系统为什么还要保留 Redis 快照及相关的延迟落库队列（ZSet dirty/processing）？
  > 2. 5,000 ~ 10,000 人同时在线答题时，频繁保存快照会产生写风暴，前端和服务端分别是如何防范的？

* **我的实答**：
  > 1. Redis 的延迟队列用于在考试过程中异步落库，把每道题的答案存入到真正的答案表中。如果去除 Redis 只靠 MySQL，意味着在考试中要批量清空旧答案和批量插入新答案，对 MySQL 的压力非常大；
  > 2. 前端有 400ms 的防抖，并且考生更新答案后会存放在 IndexedDB 中，不会立刻发送网络请求。前端维护了一个 30s 的同步周期，到期时检查是否有数据更改，没有则不发送新的答题记录。服务端在保存快照时，在单张表内存入快照的 GZIP 压缩字段，减少数据库访问次数。

* **面试官点评与得分**：**9.0 / 10（非常扎实）**
  * **得分点**：指出了非常核心的参数细节（400ms 防抖、IndexedDB 本地缓存、30s 周期轮询脏数据），并一针见血指出了直接操作 `submission_answer` 题表明细会引发大量的 `DELETE + INSERT`。
  * **代码映射**：前端 [`ExamDoing.vue:352, 1351-1360`](../../src/main/resources/frontend/src/views/student/ExamDoing.vue#L352)、[`examDraftStore.js`](../../src/main/resources/frontend/src/utils/examDraftStore.js)、后端 [`SnapshotFlushQueue.java`](../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/SnapshotFlushQueue.java)。

* **推荐口述定稿（10 分）**：
  > “面对数千人同时答题，我们构建了‘前端防抖与离线暂存 → 服务端单行降维写 → 后台异步削峰落库’三道防线：
  > 
  > 1. **前端第一道防线**：考生每次选选项或敲字，先触发 **400ms 防抖**写入本地 **IndexedDB**，绝不实时发起网络调用；同时前端挂载 **30 秒同步定时器**，只有存在未同步改动（`dirty=true`）时才向服务端发一次快照。断网时请求自动存入 IndexedDB 的 `syncQueue` 离线队列，网络恢复后幂等重放。
  > 2. **服务端快照接收层**：快照接口**绝不直接操作题目明细表**，而是写入单张主键覆盖表（`submission_draft_payload`）。将全卷答案打包为单行 JSON 并用 **GZIP 压缩**（压缩比超 70%），利用 `ON DUPLICATE KEY UPDATE` 单行更新。高并发下 MySQL 面对的只是单行主键轻量写入，避免了多行锁争用与索引分裂。
  > 3. **Redis 异步落库队列**：Redis 延迟落库队列（ZSet dirty 集合，默认 15 分钟延迟）的作用，是在考试中后期将答案平滑、低频地拆解入真正的题目明细表（`submission_answer`），彻底避免在答题高峰期频繁执行‘清空旧答案 + 批量插入 50 道新答案’把数据库打瘫痪。”

* **可能的高频追问**：
  1. *追问*：Redis 延迟队列中若有脏快照因断网或死机反复落库失败怎么办？
     * *应对思路*：协调器按退避策略重试，重试耗尽后判定为毒药消息（Poison Message），移入隔离集合（`exam:snapshot-flush:failed`）并报警，避免阻塞主落库队列。

### 问题 2.2：主观题并发批阅缺陷与防御性修复（重磅高分题）
* **面试官提问**：
  > 老师 A 和老师 B 在各自电脑上同时打开待批列表，同时看到了张三的第 5 题简答题，老师 A 给 8 分提交，老师 B 给 6 分提交。
  > 1. 系统会发生什么？会不会重复插入打分记录？最终成绩如何？
  > 2. 如果存在并发缺陷，你会如何优雅、彻底地进行重构修复？

* **我的实答**：
  > 在当前系统中，确实存在并发阅卷时的并发缺陷。当多名老师同时点击提交阅卷结果时，会有数据库的排它锁进行一个先后的更新。假设老师 A 先获取排它锁，老师 B 在阻塞等待。老师 A 事务提交释放行锁后，老师 B 获得锁继续执行。但是老师 B 没有判断这个的状态是否为 pending，因此老师 B 仍然会成功更新。这就导致最后的计分结果是两者评分之和。  
  > 要防止评分的重复提交，首先要对数据库进行修改，将数据库表增加唯一约束，防止对同一题目存在多条打分记录。然后就是在事务方面要修改它的 SQL 语句。在插入评分的时候，必须判断这道题目是否是 pending 状态。

* **面试官点评与得分**：**10 / 10（惊艳全场）**
  * **得分点**：穿透了代码表象，指出了实际存在的代码级并发缺陷：
    1. 前置 SELECT 为普通快照读，无排他性；
    2. `subjective_grade` 打分明细表缺失唯一约束；
    3. 后置 UPDATE 遗漏了 `WHERE status='PENDING'` 原子条件；
    4. `recalculate` 盲目使用 `sum(score)` 导致双重打分累加。
  * **代码映射**：[`GradingService.java:33-34`](../../services/exam-grading-service/src/main/java/com/ekusys/exam/grading/service/GradingService.java#L33-L34)、[`V1__grading_schema.sql:4-8`](../../services/exam-grading-service/src/main/resources/db/migration/V1__grading_schema.sql#L4-L8)。

* **推荐口述定稿（10 分）**：
  > “当前代码在极端并发批阅时确实存在‘打分累加’漏洞：前置查询未加锁，两事务各自查出任务后，老师 A 插入打分记录并更新状态为 `GRADED`（持有行锁）；老师 B 虽阻塞在 `update grading_task` 上，但该语句仅根据主键 `WHERE id=?` 更新，缺少状态判断。因此老师 A 提交后老师 B 仍能成功执行更新，且因 `subjective_grade` 缺少任务唯一约束，导致两张打分记录并存，最终 `recalculate()` 按照 `sum(score)` 汇总出两者分数之和。
  > 
  > 彻底修复此问题，我会构建‘三道防线’：
  > 
  > 1. **代码与事务防线（反转执行顺序，做原子 CAS 更新）**：
  >    在事务中将执行顺序改为**先原子更新状态**：
  >    ```sql
  >    UPDATE grading_task 
  >       SET status = 'GRADED', assigned_teacher_id = ?, update_time = current_timestamp(3)
  >     WHERE id = ? AND status = 'PENDING';
  >    ```
  >    检查受影响行数：若 `affectedRows == 1` 则继续执行打分插入和重算；若 `affectedRows == 0` 说明被其他老师抢先提交，直接抛出 `BusinessException("该题已被其他老师批阅")` 回滚事务。
  > 2. **数据库底层防线（唯一索引兜底）**：
  >    为打分表增加唯一物理约束：
  >    ```sql
  >    ALTER TABLE subjective_grade ADD UNIQUE KEY uk_grading_task(grading_task_id);
  >    ```
  >    即使上层业务并发击穿，数据库层面也会抛出 `DuplicateKeyException` 强制回滚，物理上杜绝多条记录产生。
  > 3. **业务体验升级（认领与租约机制 Claim & Lease）**：
  >    引入任务认领机制，老师在大厅点击批阅时，系统先执行一次轻量 CAS 认领（标记为 `CLAIMED` 并写入 5 分钟租约），其他老师界面自动置灰该题；批阅完成后直接结算，若超时未提交租约释放回 `PENDING`，彻底杜绝提交时的冲突挫败感。”

## 领域三：客户端单活租约与防多开防作弊（Client Lease、心跳与换机接管）

### 问题 3.1：为什么必须服务端租约？Chrome 与 Edge 多开冲突分析
* **面试官提问**：
  > 1. 为什么不能仅靠前端技术（如 `localStorage`、`BroadcastChannel`）防多开，必须由后端实现客户端租约？
  > 2. `clientId` 和 `leaseToken` 分别代表什么？
  > 3. 学生在 Chrome 正常作答，突然又在 Edge 打开同一场考试，两个窗口分别会发生什么？

* **我的实答**：
  > 本项目不能依靠前端浏览器技术来防止多开窗口，是因为可以使用多种方法来跳过浏览器的限制，比如跨浏览器、跨设备隐身模式等，所以必须要在服务器端实现防止多开窗口。在本系统的设计中，client ID 是窗口的 ID，lease token 代表这个心跳的令牌。系统通过这两个东西来保证只存在一个活跃的 client ID，并且令牌有效。假如学生在 Chrome 浏览器进行作答，又在 Edge 浏览器打开同一场考试，那么他在 Edge 浏览器就会打开失败，因为首先是他的 client ID 与数据库中的不一致，并且他没有令牌。

* **面试官点评与得分**：**7.5 / 10（方向正确，需强化机制术语）**
  * **得分点**：指出了前端在跨浏览器、跨设备时的无能为力；准确判断出 Edge 会失败而 Chrome 正常。

### 问题 3.2：断电死机合法换机接管与高频心跳优化
* **面试官提问**：
  > 1. 如果学生电脑意外断电死机，借室友电脑登录，新电脑会被永久卡住吗？如何安全接管？需要等待多久？

* **我的实答**：
  > 对于第一个问题，当旧电脑的答题窗口在 90 秒内没有活跃，比如续租或者答题，那么它的 token 就会过期。此时，新窗口就可以申请新的租约，进入答题界面。对于第二个问题，如果有 5000 名学生，每 30 秒发一次新旧租约，在续租的过程中，本系统是使用 Redis 的 Lua 脚本原子地进行校验和续约。当 Redis 不可用的时候，会降级到 MySQL。

* **面试官点评与得分**：**8.5 / 10（机制把握准确）**
  * **得分点**：准确说出 **90 秒超时释放**（3 个心跳周期 30s × 3）；指出使用 Redis Lua 脚本（`RENEW_SCRIPT`）内存原子续约，兼顾高性能与防击穿。
  * **代码加分项补充**：点出代码中 `persistenceInterval`（5 分钟降频同步写库）的降维设计。
  * **代码映射**：[`ExamClientLeaseService.java:90-120`](../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/ExamClientLeaseService.java#L90-L120)。

* **推荐口述定稿（10 分）**：
  > “1. **断电换机安全接管**：
  > 系统的租约 TTL 设为 **90 秒**（即 3 次心跳丢失容忍阈值）。若旧电脑断电，90 秒内无续租或答题，Redis 中的租约键自动过期，MySQL 中的租约时间也已过期。此时新电脑调用 `acquire()`，通过条件更新 `WHERE active_client_lease_until <= now` 成功抢占并生成全新的 `leaseToken`。旧电脑就算重新开机，由于拿着失效的旧 Token，发出的心跳或快照会被全部拒绝并强制踢下线。
  > 
  > 2. **高频心跳的抗压架构**：
  > 系统采用‘Redis 内存快路径 + 降频异步写库’机制：
  > - 客户端每 30 秒发一次心跳，全部由 Redis 的 `RENEW_SCRIPT` Lua 脚本在内存中原子刷新 TTL 和活跃时间，耗时 < 1ms，对数据库 0 压力；
  > - **降频持久化（`persistenceInterval`）**：Lua 脚本内部维护了 `lastPersistedEpochMs`，只有当距上次持久化超过 **5 分钟**时才返回 `persist='1'`，服务端才同步一次 MySQL。心跳虽是 30s 一次，但写库被大幅降频到 5 分钟一次，写库负载直接降低了 90%！”

## 领域四：超时自动交卷与并发控制（XXL-Job、SKIP LOCKED 与锁顺序）

### 问题 4.1：超时自动交卷完整链路与任务模型设计
* **面试官提问**：
  > 请介绍超时自动交卷完整流程，为什么不能依赖前端倒计时交卷？为什么要单独建 `submission_timeout_task` 任务表？

* **推荐口述定稿（10 分）**：
  > “前端倒计时不可信，因为客户端时间可被篡改，且考生可能断网、死机或恶意关闭浏览器，服务端必须具备权威的到期收卷能力。
  > 
  > 流程上：
  > 1. **预置与激活**：考试发布并预置考生时，预创建 `WAITING` 状态的超时任务；学生进入答题后计算服务端绝对截止时间，激活为 `PENDING`；
  > 2. **任务领取（短事务）**：XXL-Job 周期性调度 Runtime 执行器，多实例在短事务中通过 `SELECT ... FOR UPDATE SKIP LOCKED` 批量领取到期任务，避免实例间互相阻塞。领取后将任务标记为 `PROCESSING`，生成唯一 `claimToken` 与 60 秒处理租约；
  > 3. **长任务脱水与答案固化（事务外）**：耗时操作不持有行锁，依靠任务租约维持处理权。读取 MySQL 持久草稿与 Redis 快照并比对单调版本号，取最新有效载荷，编码压缩为带 SHA-256 的不可变最终载荷；
  > 4. **最终原子提交（本地短事务）**：重新锁定任务与会话，二次校验 `claimToken` 与租约，写入最终答案表，将提交记录置为 `PROCESSING`，写入 `SubmissionAccepted` Outbox 事件，会话置为 `SUBMITTED`，任务标记为 `DONE`；
  > 5. **事件投递与阅卷**：Outbox 发布器异步扫描事件，通过 Publisher Confirm 发往 RabbitMQ，下游 Grading 服务经 Inbox 去重后异步判分。
  > 
  > 之所以独立建任务表，是为了避免全表扫描大体积的会话表，且任务表能清晰记录重试次数、租约状态、执行实例与失败退避时间，方便多实例抢占和故障自愈。”

### 问题 4.2：手工交卷 vs 自动交卷的并发竞争
* **面试官提问**：
  > 考生在 10:00:00 截止瞬间点击手工交卷，此时超时交卷刚好也在执行，两条链路如何保证最终只提交一次？

* **推荐口述定稿（10 分）**：
  > “系统通过**统一加锁顺序**与**带条件的原子状态迁移**保证严格的互斥与幂等：
  > 
  > 两条链路遵循完全一致的加锁顺序：
  > `超时任务(submission_timeout_task) → 考试会话(exam_session) → 提交记录(submission) → Outbox`
  > 首先锁定同一条超时任务行，因此数据库在物理上将两流程完全串行化，杜绝死锁。
  > 
  > - **手工交卷先拿锁**：校验数据库当前时间 `deadline_time > now(3)` 且状态为 `ANSWERING`，校验成功将会话推进到 `AUTO_SUBMITTING` 并完成交卷；后续超时任务执行时，见任务已为 `DONE` 或会话为 `SUBMITTED`，直接幂等退出；
  > - **超时交卷先拿锁**：若超时流程已接管，将会话更新为 `AUTO_SUBMITTING`。等待锁释放的手工交卷被唤醒后，发现状态不再是 `ANSWERING`，直接向前端返回 `SUBMITTING`（正在交卷，请等待），杜绝二次重复提交。”

## 领域五：Transactional Outbox 与跨服务最终一致性（可靠消息与 Inbox 去重）

### 问题 5.1：双写不一致与故障重试边界
* **面试官提问**：
  > 1. 业务提交成功但 RabbitMQ 不可用怎么办？
  > 2. 消息发送成功但更新 Outbox 为 PUBLISHED 前实例宕机怎么办？
  > 3. Outbox 与 Inbox 是否能实现 Exactly-Once？

* **推荐口述定稿（10 分）**：
  > “1. **杜绝双写不一致**：
  > 若先写 DB 后发 MQ，MQ 发送失败会导致交卷成功但永远不评分；若先发 MQ 后写 DB，DB 回滚会导致下游为一份无效提交判分。因此我们将业务更新与 `SubmissionAccepted` 事件作为一条记录写入 MySQL 本地同一个事务，网络发 MQ 放到事务提交之后。即使 RabbitMQ 宕机，事件也绝不丢失；
  > 
  > 2. **发布重试与租约机制**：
  > Outbox 发布器扫描待发送事件并生成发送租约。MQ 发送失败会记录重试次数并设置指数退避时间。若消息成功发送至 MQ，但将状态更新为 `PUBLISHED` 时发布器宕机，租约到期后其他发布器实例会重新发送，因此系统提供的是**至少一次投递（At-least-once）**，必然伴随重复消息的可能；
  > 
  > 3. **消费端 Inbox 幂等消费**：
  > 下游 Grading 服务通过唯一事件 ID 写入 `inbox_event` 表，与评分落库处于同一个本地事务中。重复消息到达时触发唯一索引冲突直接忽略。若评分过程中发生业务异常，Inbox 记录随之回滚，下次 MQ 重试仍可正常进入。因此整个系统的可靠性语义是‘**至少一次投递 + 幂等消费 = 最终一致性**’，绝不能声称是绝对的 Exactly-Once。”

  > 
  > 1. **事件采集**：
  >    前端页面监听并上报 5 类典型事件：`WINDOW_BLUR`（窗口失焦）、`TAB_HIDDEN`（切换标签页）、`FULLSCREEN_EXIT`（退出全屏）、`OFFLINE`（网络离线）以及 `COPY/PASTE`（剪贴板事件），携带发生时间与离屏持续时长（`duration_ms`）；
  > 2. **服务端规则计分模型**：
