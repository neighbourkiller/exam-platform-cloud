# 超时交卷 V2 确定性接管验证与客户端延迟诊断报告

## 1. 结论先行

本轮已按计划完成：

- 200 人确定性接管机制测试四轮（领取后杀两轮、续租后杀两轮）；
- 1,000 人诊断冒烟一轮；
- 10,000 人普通对照：正常一轮、MySQL 暂停一轮；
- 10,000 人诊断轮：正常三轮、MySQL 暂停三轮，按正常/故障交替执行；
- 诊断后的普通对照：正常一轮、MySQL 暂停一轮；
- 按会话诊断、数据库权威时间线、时钟偏差、固定实例采样和原始退出码封存。

最终判断：

1. 确定性接管机制有可复核证据，四轮机制证据均为 PASS。
2. 诊断会话映射没有失败；1,000 人冒烟抽样 100/100 完成，10,000 人诊断轮每轮抽样 1,000/1,000 完成。
3. 客户端 45 秒 P99 门槛没有稳定通过。正常诊断轮客户端 P99 为 41.464s、52.284s、51.039s；诊断后普通正常对照为 49.053s。MySQL 故障轮客户端 P99 为 45.693s、57.726s、59.294s、60.029s。
4. MySQL 故障下数据库 P99 也出现 48.864s、52.322s、56.033s 的失败；任务在 due_at+60s 内最终均达到 DONE，但这不能替代客户端 SLA，也不能掩盖故障轮的 Outbox 未即时发布状态。
5. 因此本轮不调整 SLA、领取策略、线程池、连接池、租约、跨片等待或前端轮询，不开启主环境 V2。结果只能说明接管机制可复现、延迟有可复核分段证据，不能作为生产容量放行证明。

| 诊断 MySQL 3 | 40179 / 56028 / 56232ms | 4675 / 10402 / 11641ms | 8671 / 8993ms | 10098 / 11996ms |

主要观察：

- 六轮中每轮抽样的 1,000 个会话均完成了诊断解析；不是映射失败后继续堆积的结果。
- 所有抽样会话的分类都是 POLL_WAIT_DOMINANT。这是按观测时间线的分类，不等同于已经证明某一个具体组件是唯一根因。
- 状态来源中实际出现 DATABASE_FALLBACK、INFLIGHT_CACHE 和 FINAL_PROJECTION_CACHE，说明客户端看到最终状态前并非只有单一路径。
- 诊断 MySQL 1 的抽样最慢样本包括 session 890000004461：任务完成 49.033s、数据库完成后到客户端观察 8.804s、6 次状态请求。
- 诊断 MySQL 2 的抽样包含 session 890000009951：任务完成 52.456s，但在客户端截止线前没有最终观察；该抽样之外的 k6 聚合结论为 105 个未完成会话。
- 诊断 MySQL 3 的抽样包含 session 890000009991、890000009961、890000009951：任务完成约 56.2s，但客户端未在截止线前观察到最终状态；该轮 k6 聚合为 518 个未完成会话。

不能用 DB P99 与客户端 P99 的差值替代上述同一 session 的分段数据。当前证据支持：MySQL 窗口会显著拉长 Runtime 任务完成时间，完成后仍存在数秒级的状态观察和轮询等待；但网关、Runtime 状态查询、连接池和数据库等待各自的因果占比仍未被本轮单独证明。

## 7. 根因结论边界

### 已证明

- 观察组件可以在隔离配置中确定性捕获领取后和续租后的在途任务，普通 JAR 不带阻塞实现。
- 目标实例被杀后，其他实例能以新 attempt/new token 接管并最终完成；没有靠手工改状态、租约或尝试次数制造恢复。
- 普通和故障轮的 Runtime 本地任务最终都能收敛到 DONE，但 MySQL 故障会使 DB P99 和客户端 P99 失败。
- 客户端超限不是单纯数据库记录时间能解释的聚合差值；同一会话时间线显示轮询等待、状态请求和数据库完成后可见性均存在可观测区间。

### 证据支持但未完全证明

- MySQL 暂停造成的恢复、连接/事务等待和状态查询拥塞共同推动了故障轮的长尾。
- 即使数据库已记录完成，客户端仍可能等待下一次轮询或经历状态查询处理延迟。
- POLL_WAIT_DOMINANT 在六轮抽样中一致出现，说明轮询/观察策略是重要候选方向；但本轮没有实施对照性轮询修改，不能直接把它写成唯一根因。

### 仍未知

- 网关、Runtime、Hikari、MySQL 恢复后的具体等待占比；
- RabbitMQ、Grading、Reporting 真实链路在故障窗口内的端到端可见性和告警送达；
- 与生产资源隔离、网络拓扑、镜像发布状态一致时是否仍复现相同分布；
- 观察组件与同机负载之间的精确资源开销。普通/诊断结果存在明显实验波动，不能据此声称观察开销为零。

## 10. 后续决策

本轮不执行性能优化、不修改 SLA、不调整主环境配置、不发布灰度开关。若继续推进，应先在资源隔离、干净候选镜像和真实告警/Grading/Reporting 链路下复现：

1. 保留按会话时间线，继续区分任务完成、数据库完成后等待、状态请求处理和缓存/数据库可见性。
2. 以故障轮的 Outbox、RabbitMQ、Grading、Reporting 终态作为独立门槛。
3. 先解决或解释采样缺样和 k6 退出码，再谈容量结论。
4. 在有充分证据后再评估轮询策略、状态可见性和服务端阶段优化；本轮不直接实施。

在 clean candidate、分离资源、故障/告警、真实跨服务链路、按考试灰度和回滚演练全部完成前，保持主环境 APP_TIMEOUT_SUBMISSION_V2_ENABLED=false。
