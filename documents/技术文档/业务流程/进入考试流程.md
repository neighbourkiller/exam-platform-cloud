## 1. 流程总览

当前微服务实现包含两条进入考试路径：

1. V2 三段式入口：`prepare → activate → paper-delivery`。
2. `/start` 兼容入口：有 Runtime 本地考试投影时复用 V2 内部能力；没有本地投影时走旧的动态建会话流程。

考试发布后，Management 先冻结试卷快照和考生名单，并通过 Outbox 发布 `ExamPublished`。Runtime 幂等消费事件，提前创建考生会话、Submission 和超时任务，并预热不可变试卷。学生进入答题页后，前端先建立本机窗口保护，再根据开关选择 V2 或兼容入口。真正的考生资格、会话状态、个人截止时间和单活客户端由 Runtime 校验。

```mermaid
flowchart TD
    A[教师发布考试] --> B[Management 冻结试卷快照和考生名单]
    B --> C[同一事务写 ExamPublished Outbox]
    C --> D[RabbitMQ exam.events]
    D --> E[Runtime 幂等消费生命周期事件]
    E --> F[分批预创建 Session / Submission / Timeout Task]
    F --> G[预热不可变试卷到 Runtime L2/L1]
    G --> H[Runtime Definition = READY]
    H --> I[学生列表与考前检测]
    I --> J[答题页创建 clientId 并取得本机窗口保护]
    J --> K{前端 V2 是否开启}
    K -->|是| L[prepare 候场取票]
    L --> M[按稳定 slot 等待]
    M --> N[activate 激活会话与租约]
    N --> O[paper-delivery 交付试卷与服务端草稿]
    K -->|否| P[/start 兼容入口]
    L -.V2 关闭或接口 404.-> P
    P --> Q{Runtime 是否已有本地投影}
    Q -->|是| R[legacyStart 复用预创建数据]
    Q -->|否| S[旧流程同步获取准入信息并动态建会话]
    R --> T[返回完整答题数据]
    S --> T
    O --> T
    T --> U[恢复本地草稿并启动倒计时/心跳/快照/监考]
```

## 2. 系统边界与权威数据

| 组件 | 当前职责 | 数据边界 |
| --- | --- | --- |
| Frontend | 学生考试列表、考前检测、本机窗口保护、入口路径选择、候场重试、草稿恢复、倒计时和监考交互 | 负责客户端体验，不决定最终资格、Session 状态或 deadline |
| Gateway | 将 `/api/v1/exams/**` 路由到 Runtime，并对 V2 三段式入口执行 Redis 令牌桶限流 | 只保护入口流量，不维护考试业务状态 |
| Management | 发布和终止考试、冻结名册、保存试卷快照引用、写考试生命周期 Outbox | 考试定义、发布状态和冻结考生名单的来源 |
| Content | 创建和返回不可变试卷快照 | 试卷快照内容的来源 |
| Runtime | 保存考试本地投影，预创建会话，签发候场票据，激活会话，计算个人 deadline，维护客户端租约，交付试卷和处理答题快照/交卷 | 运行期 Session、Submission、deadline 和租约的权威边界 |
| Runtime Redis | 保存候场票据、试卷 L2 缓存、客户端租约快路径、答题快照队列 | 快路径和缓存；关键状态仍通过 Runtime MySQL 约束 |
| Runtime MySQL | 保存 `runtime_exam_definition`、`exam_session`、`submission`、`submission_timeout_task`、草稿载荷、Outbox 和 Inbox | Runtime 持久化业务状态 |
| RabbitMQ/Outbox | 传递 `ExamPublished`、`ExamTerminated`、`SessionStarted`、`SubmissionAccepted` 等事件 | 使用“至少一次投递 + 消费端幂等”语义 |
| Reporting | 消费考试和运行期事件，建立查询、监考和报表投影 | 查询投影，不反向控制 Runtime 入场 |

## 3. 当前入口模式与默认配置

### 3.1 仓库默认值

- 前端以 `VITE_EXAM_ENTRY_V2_ENABLED !== 'false'` 判断是否使用 V2，因此未显式配置时默认尝试 V2。
- Runtime 的 `app.exam-entry.enabled` 默认读取 `${APP_EXAM_ENTRY_V2_ENABLED:false}`。
- `docker-compose.yml` 默认向 Runtime 注入 `APP_EXAM_ENTRY_V2_ENABLED=false`。
- Runtime 对 `ExamPublished` 的消费、数据预创建和试卷预热不受 V2 API 开关控制。

### 3.2 路径选择

| 前端选择 | Runtime 状态 | 当前执行路径 |
| --- | --- | --- |
| V2 开启，Runtime V2 开启且投影为 `READY` | 本地投影和预创建会话存在 | `prepare → activate → paper-delivery` |
| V2 开启，Runtime V2 关闭 | `prepare` 返回 `EXAM_ENTRY_V2_DISABLED` | 前端回退到 `/start` |
| V2 开启，但 V2 API 返回 404 | 可能是兼容部署 | 前端回退到 `/start` |
| V2 开启，投影仍为 `PROVISIONING` 或 `FAILED` | Runtime 尚未达到可入场状态 | `prepare` 返回 `EXAM_PREPARING`，前端在总计 30 秒的入场重试窗口内重试 |
| 前端 V2 关闭 | 不区分 Runtime V2 开关 | 直接调用 `/start` |
| `/start` 且 Runtime 已有本地投影 | 使用预创建数据 | `ExamEntryService.legacyStart` |
| `/start` 且 Runtime 没有本地投影 | 使用旧流程 | `ExamRuntimeService.start` 同步读取 Management 准入数据并动态创建会话 |

Gateway 的专用入场限流当前匹配以下三个 POST 路径：

- `/api/v1/exams/{id}/entry/prepare`
- `/api/v1/exams/{id}/entry/activate`
- `/api/v1/exams/{id}/paper-delivery`

仓库默认令牌桶参数为：`prepare` 500/s、burst 1000；`activate` 和 `paper-delivery` 均为 1200/s、burst 2400。`/start` 不属于该过滤器的匹配范围。

## 4. 发布、冻结与 Runtime 预创建

### 4.1 Management 发布考试

教师发布考试时，Management 在本地事务中执行：

1. 仅允许状态为 `DRAFT` 的考试发布。
2. 调用 Content 为试卷创建不可变快照。
3. 按目标教学班从 Academic 读取名册，将学生、教学班和名册版本写入 `exam_candidate`。
4. 将快照 ID 和版本写入 `exam_paper_ref`。
5. 将考试状态改为 `PUBLISHED`。
6. 在同一事务中写入 `ExamPublished` v2 Outbox。
7. 事务提交后刷新 Management 的 Runtime 元数据缓存，并触发试卷缓存预热调用。

`ExamPublished` v2 事件包含考试时间、时长、及格分、快照 ID/版本、监考配置、`candidateCount` 和完整考生列表。Outbox 发布器将事件投递到 `exam.events`。

主要实现：

- [`ExamManagementService.java`](../../../services/exam-management-service/src/main/java/com/ekusys/exam/management/service/ExamManagementService.java)
- [`ManagementOutboxService.java`](../../../services/exam-management-service/src/main/java/com/ekusys/exam/management/messaging/ManagementOutboxService.java)

### 4.2 Runtime 消费生命周期事件

Runtime 的独立生命周期队列绑定 `ExamPublished` 和 `ExamTerminated`：

1. 消费者解析 `eventId`、事件版本和考试 ID。
2. v2 发布事件直接读取载荷中的考生列表，并要求 `candidateCount` 与列表数量一致。
3. v1 发布事件通过 Management 的 `proctoring-context` 接口补全考试元数据和考生列表。
4. 消费失败按仓库默认参数最多尝试 3 次，最终进入 `exam.runtime.exam-lifecycle.dlq`。

Runtime 使用 `inbox_event` 和固定消费者名保证同一生命周期事件幂等处理。

### 4.3 预创建和预热

Runtime 收到 `ExamPublished` 后：

1. 将 `runtime_exam_definition` 写为 `PROVISIONING`。
2. 对考生 ID 去重排序，并按默认 500 人一批执行预创建。
3. 每名考生对应创建或补齐：
   - `exam_session`：通常为 `PREPARED`，不设置 `start_time` 和 `deadline_time`；
   - `submission`：`IN_PROGRESS`，绑定试卷快照；
   - `submission_timeout_task`：未开始会话为 `WAITING` 且 `due_at=NULL`，已存在的活跃会话使用 `PENDING` 和原 deadline。
4. 校验 Session、Submission、Timeout Task 的学生数量均与冻结考生数一致。
5. 从 Content 加载指定版本的不可变试卷，写入 Runtime Redis L2，并放入当前实例 Caffeine L1。
6. 将本地考试投影改为 `READY`，更新已准备人数并记录 Inbox。

如果处理失败，Runtime 将投影标为 `FAILED` 并让消息处理失败，以便 RabbitMQ 重试或进入 DLQ。若 `ExamTerminated` 已先到达，后到的发布事件不会把本地投影从 `TERMINATED` 改回可入场状态。

## 5. 学生列表、考前检测与本机窗口保护

### 5.1 学生考试列表

1. Frontend 调用 `GET /api/v1/exams/student`。
2. Runtime 从 Management 获取该学生的考试摘要，并用本地 Submission 判断是否已经提交。
3. 前端不允许已提交、`FINISHED`、`TERMINATED` 或已超过结束时间的考试进入。
4. 前端按浏览器时间在开考前 10 分钟开放“进入考试”按钮。

### 5.2 考前检测

从考试列表进入时，前端弹窗检查浏览器能力、网络、多显示器、屏幕共享、摄像头和麦克风。强制项通过后跳转到 `/student/exam/{id}`。当前路由守卫校验登录状态和 `STUDENT` 角色；检测结果本身不作为 Runtime `prepare` 或 `activate` 的请求字段。

### 5.3 clientId 和同浏览器窗口保护

答题页启动时：

1. 前端从 `sessionStorage` 读取或创建当前用户、当前考试对应的 `clientId` 和已有 `leaseToken`。
2. 优先通过 Web Locks 请求 `exam-window:{userId}:{examId}` 的非阻塞锁。
3. Web Locks 不可用或调用失败时，通过 BroadcastChannel 等待短暂选举窗口，并按实例启动时间和实例 ID 确定一个活动窗口。
4. 检测到另一活动窗口后，当前入场流程会被取消，尚在等待或执行中的 HTTP 请求通过 `AbortController` 中止。
5. 浏览器不支持上述两种能力时，本机保护模式为 `none`，最终仍由 Runtime 客户端租约裁决单活客户端。

## 6. V2 三段式进入考试

### 6.1 第一段：`prepare`

请求：`POST /api/v1/exams/{id}/entry/prepare`

1. Gateway 按考试 ID 和 `prepare` 维度执行令牌桶限流。
2. Runtime 要求 `app.exam-entry.enabled=true`，并从 MySQL 获取 `current_timestamp(3)`。
3. 本地考试投影必须为 `READY` 或 `TERMINATED`；其他状态返回 `EXAM_PREPARING`。
4. 当前用户必须存在对应的预创建 Session，否则返回 `EXAM_NOT_CANDIDATE`。
5. 已终止考试或 `CANCELLED` Session 返回 `TERMINATED`；已进入终态的 Session 返回 `SUBMITTED`。
6. 候场开放时间为 `startTime - waitingRoomMinutes`，仓库默认提前 10 分钟；过早进入返回 HTTP 425 和 `retryAfterMs`。
7. 到达考试结束时间后返回 `EXAM_ENTRY_CLOSED`。
8. Runtime 计算稳定 slot：`SHA-256(examId:studentId) mod slotCount`，默认 10 个 slot；计划激活时间为 `startTime + slot 秒`。
9. Redis 票据绑定 `examId + studentId + clientId + slot + scheduledAt`。同一学生和客户端重复调用会复用票据，票据保留到考试结束时间再加默认 10 分钟。
10. 返回 `WAITING` 或 `READY`、服务器时间、计划激活时间、slot 和票据。

前端使用服务端时间与计划激活时间的差值等待，不使用浏览器绝对时钟重新计算开考时刻。

### 6.2 第二段：`activate`

请求：`POST /api/v1/exams/{id}/entry/activate`

1. Gateway 按考试 ID 和 `activate` 维度限流。
2. Runtime 校验票据必须与当前考试、学生和 `clientId` 一致。
3. V2 路径在计划激活时刻之前返回 HTTP 425；前端等待服务端给出的时间后重试。
4. Runtime 拒绝已经结束或终止的考试，并识别已提交或正在自动交卷的 Session。
5. 在改变 Session 状态前，先从 Caffeine L1、Redis L2 或 Content single-flight 加载并核对试卷快照 ID 和版本。
6. 激活短事务使用数据库时间，并按 Timeout Task → Session 的顺序协调并发：
   - 只有 `PREPARED` Session 可原子变为 `ANSWERING`；
   - `start_time` 取数据库当前时间；
   - `deadline_time = min(start_time + durationMinutes, examEndTime)`；
   - 生成初始 `leaseToken`，把 `clientId`、token 和租约时间写入 Session；
   - 将对应 Timeout Task 从 `WAITING` 改为 `PENDING`，`due_at=deadline`；
   - 在同一事务中写确定性的 `SessionStarted` Outbox。
7. 并发重复激活时，只有一个请求能完成 `PREPARED → ANSWERING`；后续请求读取现有状态，并按 `RESUMED` 或终态返回。
8. MySQL 激活事务提交后，Runtime 将相同 token 严格激活到 Redis。已有同客户端 token 可以恢复；新客户端只能在旧租约不存在或已过期时接管。
9. 返回 Session 开始时间、全局结束时间、个人 deadline、租约 token、租约过期时间和心跳参数。

个人答题计时从 Session 成功变为 `ANSWERING` 时开始。

### 6.3 第三段：`paper-delivery`

请求：`POST /api/v1/exams/{id}/paper-delivery`

1. Gateway 按考试 ID 和 `paper-delivery` 维度限流。
2. Runtime 要求 Session 为 `ANSWERING`。
3. Runtime 通过 MySQL 条件更新校验 `clientId + leaseToken`、Session 状态和数据库当前 deadline，同时刷新客户端活跃时间。
4. 再次读取并核对不可变试卷快照。
5. 首次交付使用一条条件更新写入 `first_paper_delivered_at`；条件同时包含 `ANSWERING`、deadline 未到以及当前客户端 ID/token。
6. 条件更新未命中时重新校验当前租约，用于区分合法的重复交付和已失效的会话。
7. 第一次交付返回空服务端草稿；重复进入时读取持久化草稿载荷，若不存在则从 Redis/MySQL 快照中选择较新的草稿。
8. 返回试卷静态题目、监考策略、草稿答案、草稿版本和草稿更新时间。

### 6.4 入场重试与取消

前端把 HTTP 425、429，以及除 `EXAM_ENTRY_V2_DISABLED` 外的部分 503 入口错误视为可重试错误。单次页面入场的自动重试总窗口为 30 秒：

1. 服务端返回 `retryAfterMs` 时，等待时间为该值加上有上限的随机抖动，确保不会早于服务端建议时间重试。
2. 未返回服务端等待时间时，使用从 200 ms 档开始、最高 2 秒的 full-jitter 指数退避。
3. 候场到计划激活时刻的等待不受 30 秒重试窗口限制，前端按服务器时间差逐秒更新提示。
4. 窗口冲突、组件卸载或入场被取消时，等待计时器以及 prepare、activate、paper-delivery、兼容 `/start` 请求都会停止。

主要实现：

## 7. `/start` 兼容入口

请求：`POST /api/v1/exams/{id}/start`

Runtime Controller 先判断是否存在 `runtime_exam_definition`。

### 7.1 已有 Runtime 本地投影

进入 `ExamEntryService.legacyStart`：

1. 要求投影为 `READY`；终止状态直接拒绝。
2. 使用数据库时间要求已经到达正式开考时间。
3. 内部依次执行 prepare、activate 和 paper-delivery。
4. 内部激活不等待稳定 slot，但仍校验 Redis 候场票据、预创建 Session、试卷缓存、客户端租约和 Session 状态。
5. 把三段返回值合并为旧版 `StartExamResponse`，一次返回题目、当前答案、个人 deadline、监考策略和租约信息。

### 7.2 没有 Runtime 本地投影

进入 `ExamRuntimeService.start`：

1. 通过 Management Feign 接口同步获取考生准入信息、考试元数据和试卷快照。
2. 使用数据库时间校验考试时间范围。
3. 首次进入时动态创建 `ANSWERING` Session 和 `IN_PROGRESS` Submission，计算个人 deadline，并写 `SessionStarted` Outbox。
4. 确保存在对应的超时任务，并在事务提交后激活 Redis 客户端租约。
5. 重复进入时读取已有 `ANSWERING` Session，恢复或接管有效租约。
6. 加载最新服务端草稿，并返回完整 `StartExamResponse`。

## 8. 前端答题环境初始化

三段式或兼容入口成功返回后，前端执行：

1. 保存 Runtime 返回的 `leaseToken`、租约过期时间、心跳间隔和租约超时参数。
2. 使用服务端返回的 deadline 初始化倒计时；浏览器计时只负责展示和触发状态确认。
3. 将服务端草稿合并进题目，再读取 IndexedDB 中的本地草稿。
4. 网络恢复模式下优先使用本地完整题目和本地答案；正常在线进入时，如果本地 `updatedAt` 晚于服务端 `draftUpdatedAt`，采用本地答案，否则采用服务端答案。
5. 恢复本地快照序列、服务端 revision、待交卷意图和标记题目。
6. 将选定答案重新写入 IndexedDB，随后启动：
   - 每秒倒计时；
   - 每 30 秒答题快照同步和离线队列冲刷；
   - 带随机抖动的租约心跳；
   - 每 30 秒健康检查；
   - 监考事件、摄像头、全屏和页面离开保护。
7. 如果在线入场失败，但本机已有完整题目、未过期 deadline 和既有租约，前端可以进入离线恢复模式；网络恢复后再由 Runtime 校验 Session、deadline 和租约。

## 9. 入场后的租约与答题快照

### 9.1 客户端租约

- `clientId` 区分浏览器窗口或设备，`leaseToken` 证明当前客户端持有 Session。
- Redis Lua 脚本承担心跳和快照时的原子续租快路径；租约 TTL 不超过个人 deadline。
- Redis 键不存在或不可用时，已有 token 可以通过 MySQL 中匹配的客户端字段恢复；新客户端接管不能在 Redis 不可用时降级。
- MySQL 租约信息按持久化间隔更新，供 Redis 丢失后的恢复使用。
- 试卷交付、手工交卷等关键操作通过 MySQL 条件更新再次校验当前客户端。

### 9.2 答题快照

1. 前端在 IndexedDB 保存本地答案，并为每次待同步内容生成递增 `clientSequence`，同时携带 `baseServerRevision`。
2. Runtime 在事务中锁定 Session 和当前草稿载荷，校验 Session 为 `ANSWERING`、数据库 deadline 未到，以及 `clientId + leaseToken` 匹配。
3. 相同 `clientSequence`、相同客户端和相同内容哈希按幂等成功处理；同一序列对应不同内容时返回序列冲突。
4. 客户端序列落后，或 `baseServerRevision` 与服务端不一致时，ACK 返回 `accepted=false`、当前 `serverRevision` 和已保存的客户端序列。
5. 接受新草稿时，Runtime 递增 `serverRevision`，将压缩后的完整草稿和 SHA-256 持久化到 MySQL，然后更新 Redis 快照队列。
6. 前端收到拒绝 ACK 后保留 dirty 状态，按新的服务端 revision 重新排队；网络失败时把快照放入 IndexedDB 同步队列。
7. 后台 Flush Coordinator 将 Redis 队列中的草稿批量落入 Submission 草稿/答案表。

- [`ExamSnapshotService.java`](../../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/ExamSnapshotService.java)

## 10. 交卷与截止接管

### 10.1 手工交卷

学生点击交卷时，前端先保存本地答案并尽量完成快照同步，然后携带当前租约和答案调用 `/submit`。Runtime 通过条件更新在手工交卷、自动交卷和重复请求之间裁决唯一处理者，固化最终答卷载荷，将 Submission 置为 `PROCESSING`，将 Session 收敛为 `SUBMITTED`，完成 Timeout Task，并在本地事务中写 `SubmissionAccepted` Outbox。事务提交后清理租约和临时快照。

### 10.2 deadline 到期

激活时创建的 Timeout Task 在 `due_at` 到达后由 XXL-Job/Runtime 超时处理器领取。领取过程先锁任务，再把 `ANSWERING` Session 改为 `AUTO_SUBMITTING`。工作线程加载最新草稿、固化最终载荷、更新 Submission 和 Session、完成任务并写事件。任务使用 claim token、处理租约、续租、重试和失败状态支持多实例接管。

## 11. 考试终止流程

教师在 Management 终止考试时：

1. Management 将考试状态改为 `TERMINATED`，并在同一事务中写 `ExamTerminated` Outbox。
2. Runtime 幂等消费事件，将本地考试定义改为 `TERMINATED`；后续 prepare/activate 不再允许新会话开始。
3. Runtime 在同一终止事务中按 Timeout Task → Session 的顺序锁定本场考试数据。
4. 对 `PREPARED` Session：
   - `WAITING` Timeout Task 改为 `CANCELLED`；
   - `IN_PROGRESS` Submission 改为 `CANCELLED`；
   - Session 改为 `CANCELLED` 并记录结束时间。
5. 对 `ANSWERING` Session：
   - 补齐可能缺失的 Timeout Task；
   - 将 `WAITING/PENDING` Task 置为可立即领取的 `PENDING`，并把 `due_at` 收敛到数据库当前时间；
   - 将 Session deadline 收敛到数据库当前时间。
6. 超时交卷协调器随后领取到期任务，将正在作答的 Session 转为 `AUTO_SUBMITTING`，保存最新服务端草稿并完成自动交卷。
7. 重复 `ExamTerminated` 通过 Inbox 幂等处理；后到的 `ExamPublished` 不会覆盖终止状态。

- [`ExamProvisioningService.java`](../../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/entry/ExamProvisioningService.java)
- [`TimeoutSubmissionCoordinator.java`](../../../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/TimeoutSubmissionCoordinator.java)

## 12. 主要状态迁移

```text
runtime_exam_definition:
  PROVISIONING -> READY
  PROVISIONING -> FAILED
  PROVISIONING / READY / FAILED -> TERMINATED

exam_session:
  PREPARED -> ANSWERING -> SUBMITTED
  PREPARED -> ANSWERING -> AUTO_SUBMITTING -> SUBMITTED
  PREPARED -> CANCELLED                       (考试终止且尚未开始)
  ANSWERING -> deadline 收敛到当前时间
            -> AUTO_SUBMITTING -> SUBMITTED   (考试终止后的到期接管)
  AUTO_SUBMITTING -> SUBMISSION_FAILED        (自动交卷达到失败上限)

submission:
  IN_PROGRESS -> PROCESSING
  IN_PROGRESS -> CANCELLED                    (考试终止且尚未开始)

submission_timeout_task:
  WAITING -> PENDING -> PROCESSING -> DONE
  WAITING -> CANCELLED                        (考试终止且尚未开始)
  PENDING / PROCESSING -> PENDING             (租约失联后的重试接管)
  PROCESSING -> FAILED                        (达到失败条件)
```

Runtime 的状态迁移以数据库条件更新和事务为准；浏览器窗口锁、页面倒计时和本地草稿只参与客户端体验，不能替代服务端裁决。
