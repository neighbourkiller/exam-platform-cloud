# 最新版微服务进入考试流程、缺陷与优化建议

> 分析日期：2026-08-19
>
> 代码基线：`main` / `df5c136e367472eab6ffa8051ce9a117518688bb`（`2026-08-10T08:02:48+08:00`，“实现万人考试三段式入场流程（Exam Entry V2）”）
>
> 分析范围：Frontend、Gateway、Management、Runtime、Content、Redis、MySQL、RabbitMQ/Outbox、Reporting，以及开考后立即衔接的客户端租约和草稿恢复。
>
> 结论边界：本文依据当前代码、Flyway 迁移、Nacos 源配置、`docker-compose.yml`、测试和运维文档。未读取运行中 Nacos 的最终值，也未在真实业务栈上执行万人 k6 压测，因此不将仓库默认状态等同于某个已部署环境的实时状态。

## 1. 结论摘要

最新代码的目标方案是正确的：考试发布后由 Management Outbox 发出冻结数据，Runtime 提前为考生创建 `PREPARED` 会话、`IN_PROGRESS` Submission 和 `WAITING` 超时任务，并预热不可变试卷快照。学生入场被拆成“候场取票→激活会话→交付试卷”三段，激活使用 MySQL 短事务和服务端时间，单活答题由 Runtime 租约而不是浏览器锁作为权威约束。

但当前版本还不宜直接宣称“万人入场方案已具备生产可用性”，原因不是核心并发事务测试失败——本次实测的入场相关用例全部通过——而是配置、路由和恢复语义存在以下缺口：

1. **P0：仓库默认配置实际走“V2 兼容入口”，但该入口绕过了 V2 的分槽和 Gateway 专用限流。** 前端默认开启 V2 客户端，Runtime/Compose 默认关闭 V2 API；前端收到 `EXAM_ENTRY_V2_DISABLED` 后转到 `/start`。只要 Runtime 已有本地考试投影，`/start` 仍会进入 `legacyStart` 适配器，并以 `enforceSlot=false` 激活；Gateway 限流正则又只覆盖三段式 API，不覆盖 `/start`。这使标准默认部署绕过了本次版本的主要容量保护。
2. **P0：恢复作答时忽略服务端 `draftVersion`，使用不同时钟域的时间戳决定草稿新旧，存在静默丢答风险。** 服务端已返回单调 `draftVersion`，但前端用浏览器 `updatedAt` 和服务端 `draftUpdatedAt` 比较，且初始化 `snapshotVersion` 时只读本地草稿。时钟偏快的旧本地草稿可覆盖更新的服务端草稿；时钟偏慢的新设备又可能提交一个较小版本，Redis 拒绝写入后前端仍可把 ACK 当成同步成功。
3. **P0/P1：个人计时在试卷真正交付到浏览器之前已经开始。** Runtime 在激活事务中立即将会话改为 `ANSWERING` 并计算 deadline，事务提交后才严格写 Redis 租约，再由前端调用 `paper-delivery`。Redis 租约激活、网络回包或试卷交付失败时，学生尚未看到题目却已消耗作答时间。
4. **P0：教师终止考试只清理尚未开始的会话，已在作答的学生不会被停止。** `ExamTerminated` 会把考试投影改为 `TERMINATED`，但后续 SQL 仅匹配 `PREPARED` Session、`WAITING` Timeout Task 和其 Submission；`ANSWERING` Session、`PENDING` 超时任务和有效租约不变。结果是新学生不能入场，已入场学生仍能心跳、保存和正常/超时交卷，终止语义不完整。
5. **P1：前端和 k6 重试实现没有遵守 `Retry-After`。** 服务端给出的 `retryAfterMs` 被当成随机等待的上限而不是最小等待时间，客户端常在限流窗口恢复前再次请求，可放大 425/429/503 重试风暴。
6. **P1：Management 已发布不等于 Runtime 已可入场，但学生列表没有准备状态。** Runtime 的 `PROVISIONING/READY/FAILED` 仅存在自己的 Schema 和指标中，前端从 Management 获得 `PUBLISHED` 后即可显示“进入考试”。如果发布距开考过近、消息积压或预热失败，学生只会在页面重试 30 秒后失败返回列表。
7. **P1：考前检测是可绕过的浏览器 UX，不是服务端入场条件。** 直接打开 `/student/exam/{id}` 即可绕过列表弹窗；Runtime 不知道检测是否完成。在普通 Web 浏览器中本来也无法把这类检测宣称为不可伪造的防作弊证明。
8. **P1：`ExamPublished` 是一条携带全部考生和班级名称的大消息，Reporting 消费时对每名考生执行两次单行 SQL。** 一万人场景下单条事件会膨胀，Reporting 在单事务内约执行 20,000 次写操作，这与“万人入场”目标不匹配。
9. **P1/P2：时间权威尚未完全统一。** 新入场激活和试卷交付使用 MySQL 时间，但开考后心跳和快照入口使用 JVM `LocalDateTime.now()`，页面列表和本地草稿使用浏览器 `Date.now()`。节点或设备时钟偏差会影响租约、截止时间和草稿版本判断。

综合判断：**V2 的预创建、MySQL 并发激活、票据绑定、租约校验和试卷缓存方向可保留；在修复 P0、补齐路由矩阵测试并完成真实万人压测前，不建议将当前方案作为大型正式考试的已完成交付。**

## 2. 系统边界与权威数据

| 组件 | 进入考试的职责 | 权威性 |
| --- | --- | --- |
| Frontend | 考试列表、考前检测、本机窗口锁、V2/兼容路由、草稿恢复和页面计时 | 只是体验层，不是资格、单活或 deadline 的权威源 |
| Gateway | `/api/v1/exams/**` 路由到 Runtime，对三段式入场 API 做 Redis 令牌桶限流 | 流量保护边界，不定义业务状态 |
| Management | 考试发布、冻结考生名单、试卷快照引用、发出 `ExamPublished` Outbox | 考试发布状态和冻结考生名单的权威源 |
| Runtime | 本地考试投影、预创建会话、候场票据、激活、个人 deadline、客户端租约、试卷交付、草稿 | 运行期会话、单活租约、个人 deadline 和交卷状态的权威源 |
| Content | 创建并交付不可变试卷快照 | 试卷快照内容权威源 |
| Runtime Redis | 候场票据、试卷 L2 缓存、客户端租约快路径、答题快照快路径 | 票据和快路径状态；最终会话仍由 Runtime MySQL 约束 |
| Runtime MySQL | `runtime_exam_definition`、`exam_session`、`submission`、`submission_timeout_task`、`outbox_event`、`inbox_event` | Runtime 持久化权威源 |
| RabbitMQ/Outbox | Management 到 Runtime/Reporting 的至少一次事件传递 | 传输语义是“至少一次 + 消费端幂等”，不是 exactly-once |
| Reporting | 建立考试、考生和监考投影，消费 `SessionStarted` | 查询投影，不反向控制 Runtime 入场 |

## 3. 当前“默认实际路径”与目标 V2 不同

### 3.1 仓库默认值

- [`ExamDoing.vue`](../src/main/resources/frontend/src/views/student/ExamDoing.vue) 以 `VITE_EXAM_ENTRY_V2_ENABLED !== 'false'` 判断，即前端没有显式配置时 **V2 客户端默认开启**。
- [`exam-runtime-service.yml`](../deploy/nacos-config/exam-runtime-service.yml) 将 `app.exam-entry.enabled` 绑定为 `${APP_EXAM_ENTRY_V2_ENABLED:false}`。
- [`docker-compose.yml`](../docker-compose.yml) 显式向 Runtime 注入 `APP_EXAM_ENTRY_V2_ENABLED: "${APP_EXAM_ENTRY_V2_ENABLED:-false}"`，即 **Runtime 默认关闭三段式 API**。
- [`RuntimeExamLifecycleConsumer.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/messaging/RuntimeExamLifecycleConsumer.java) 和预创建流程不受该开关限制，因此开关关闭时仍会创建 Runtime 本地投影和 `PREPARED` 会话。

### 3.2 路由决策矩阵

| 前端 V2 | Runtime V2 | Runtime 本地投影 | 实际路径 | 结果 |
| --- | --- | --- | --- | --- |
| 默认开 | 默认关 | 已存在 | `prepare` 返回 `EXAM_ENTRY_V2_DISABLED` → 前端调 `/start` → `ExamEntryService.legacyStart` | 使用预创建和缓存，但不等待 slot，不经 Gateway 三段限流 |
| 开 | 开 | `READY` | `prepare` → `activate` → `paper-delivery` | 目标 V2 流程 |
| 开 | 开 | 不存在或未 `READY` | `prepare` 返回 `EXAM_PREPARING` | 前端最多重试 30 秒，不回退 `/start` |
| 关 | 任意 | 已存在 | 直接 `/start` → `legacyStart` | 同样绕过 slot 和三段限流 |
| 关或 V2 API 404 | 任意 | 不存在 | `/start` → `ExamRuntimeService.start` | 旧动态建会话流程，每个学生同步 Feign 调 Management/Content |

因此，“V2 开关关闭”的准确含义只是“禁用三段式公开 API”，并不是“完全使用旧 Runtime 实现”。这个语义必须在配置名称、发布手册和测试中说清楚。

## 4. 完整进入考试流程

```mermaid
flowchart TD
    A[教师发布考试] --> B[Management 冻结试卷和考生名单]
    B --> C[同一事务写 ExamPublished Outbox]
    C --> D[RabbitMQ exam.events]
    D --> E[Runtime 幂等消费]
    E --> F[分批预创建 PREPARED Session / Submission / WAITING Task]
    F --> G[预热 Content 不可变试卷到 L2/L1]
    G --> H[Runtime Definition = READY]
    H --> I[学生列表和考前检测]
    I --> J{V2 三段式是否真正启用}
    J -->|yes| K[prepare: 资格/时间/稳定 slot/Redis ticket]
    K --> L[activate: 验票+校验缓存]
    L --> M[MySQL 短事务: PREPARED -> ANSWERING]
    M --> N[Task WAITING -> PENDING + SessionStarted Outbox]
    N --> O[事务后激活 Redis 租约]
    O --> P[paper-delivery: 验租约+交付题目/草稿]
    J -->|default fallback| Q[/start -> legacyStart 兼容适配]
    Q --> M
    P --> R[前端合并服务端/本地草稿]
    R --> S[启动倒计时、心跳、快照、监考]
```

### 4.1 发布和冻结阶段

1. Management 仅允许 `DRAFT` 考试发布。
2. 调用 Content 生成不可变试卷快照，按目标教学班从 Academic 获取名册，写入 Management 自己的 `exam_candidate` 和 `exam_paper_ref`。
3. 考试改为 `PUBLISHED`，并在同一 Management 本地事务中写 `ExamPublished` v2 Outbox。
4. 事件载荷包含考试元数据、试卷快照 ID/版本、监考策略、`candidateCount` 和完整 `candidates`。

主要实现：

- [`ExamManagementService.java`](../services/exam-management-service/src/main/java/com/ekusys/exam/management/service/ExamManagementService.java)
- [`ManagementOutboxService.java`](../services/exam-management-service/src/main/java/com/ekusys/exam/management/messaging/ManagementOutboxService.java)

### 4.2 Runtime 投影和预创建阶段

1. Runtime 的独立生命周期队列只绑定 `ExamPublished` 和 `ExamTerminated`，失败最多尝试 3 次后进入 DLQ。
2. v2 事件先校验 `candidateCount == candidates.size()`；v1 事件则通过 Management `proctoring-context` 补全。
3. Runtime 先写 `runtime_exam_definition.provisioning_status=PROVISIONING`，再按默认 500 人一批创建：
   - `exam_session.status=PREPARED`，不设 `start_time/deadline_time`；
   - `submission.status=IN_PROGRESS`；
   - `submission_timeout_task.status=WAITING`，`due_at=NULL`。
4. 通过三类数量与冻结考生数一致性校验后，从 Content 预热试卷到 Runtime Redis L2 和当前实例 Caffeine L1。
5. 只有预热也成功后才将投影改为 `READY` 并写 Runtime `inbox_event`；任何一步失败都保持入场失败关闭。

### 4.4 V2 第一段：`prepare`

`POST /api/v1/exams/{id}/entry/prepare`：

1. Gateway 按 `examId + prepare` 使用 Redis 令牌桶，默认补充速率 500/s，burst 1000。
2. Runtime 要求 V2 开关已开，并使用 MySQL `current_timestamp(3)` 作为服务端时间。
3. 必须存在 `READY` 或 `TERMINATED` 的本地考试投影，且当前用户必须存在预创建会话。
4. 提前进入窗口为 `startTime - waitingRoomMinutes`，默认 10 分钟；过早返回 HTTP 425，并携带 `Retry-After`/`retryAfterMs`。
5. `slot = SHA-256(examId:studentId) mod slotCount`，默认 10 个 slot；个人计划激活时间为 `startTime + slot 秒`。
6. Runtime Redis 签发 UUID 票据，绑定 `examId + studentId + clientId + slot + scheduledAt`，直到考试结束后的保留期内有效。相同学生和客户端重试会复用票据。

### 4.5 V2 第二段：`activate`

`POST /api/v1/exams/{id}/entry/activate`：

1. Gateway 默认限制 1200/s，burst 2400。
2. Runtime 核对票据与当前考试、学生、`clientId` 的绑定，未到 `scheduledAt` 则返回 HTTP 425。
3. 先通过 Caffeine L1/Redis L2/Content single-flight 读取并核对试卷快照 ID 和版本；缓存不可用时不启动个人计时。
4. 使用 READ COMMITTED、5 秒超时的 MySQL 短事务：
   - 通过 `where id=? and status='PREPARED'` 原子将 Session 改为 `ANSWERING`；
   - `start_time = dbNow`；
   - `deadline_time = min(dbNow + durationMinutes, examEndTime)`；
   - 生成初始租约 token，写 Session 中的客户端字段；
   - 将超时任务从 `WAITING` 改为 `PENDING`，`due_at=deadline`；
   - 写确定性 `SessionStarted` Outbox。
5. 并发重复激活只有一个请求能成功改变 `PREPARED`；其他请求读取已有会话并返回 `RESUMED`。
6. MySQL 事务已提交后，严格将同一 token 激活到 Redis。失败时返回可重试的 `EXAM_CLIENT_LEASE_UNAVAILABLE`，已开始的 MySQL 会话不回滚。

主要实现：

- [`ExamEntryService.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/entry/ExamEntryService.java)
- [`ExamActivationTransactionService.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/entry/ExamActivationTransactionService.java)
- [`ExamEntryTicketService.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/entry/ExamEntryTicketService.java)
- [`ExamClientLeaseService.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/service/ExamClientLeaseService.java)

### 4.6 V2 第三段：`paper-delivery`

`POST /api/v1/exams/{id}/paper-delivery`：

1. Gateway 默认限制 1200/s，burst 2400。
2. Runtime 要求 Session 必须为 `ANSWERING`，并使用 MySQL 更新条件严格校验 `clientId + leaseToken + deadline`。
3. 再次从试卷缓存取题并校验快照版本。
4. 首次调用将 `first_paper_delivered_at` 由 `NULL` 改为当前 DB 时间，返回空草稿；再次进入则从 Redis/MySQL 选取最新草稿。
5. 返回试卷静态题目、监考策略、草稿答案、`draftVersion` 和 `draftUpdatedAt`。

`first_paper_delivered_at` 实际表示“服务端已开始处理首次交付”，不能证明浏览器已收到并渲染题目。

### 4.7 前端初始化答题环境

1. 应用 Runtime 返回的租约、服务端 deadline、题目和监考策略。
2. 从 IndexedDB 读本地草稿，并与服务端草稿比较。当前实现使用 `localDraft.updatedAt > serverDraftTime` 决定采用哪份，这是本文 P0 缺陷的根源。
3. 启动服务端 deadline 倒计时、快照定时同步、租约心跳、健康检查、本机窗口锁、全屏和监考。
4. 本机无网但有完整的本地试卷与租约时，前端允许进入离线恢复模式；服务端在网络恢复后仍会校验租约和状态。

### 4.8 状态迁移

```text
runtime_exam_definition:
  PROVISIONING -> READY
  PROVISIONING -> FAILED
  *            -> TERMINATED

exam_session:
  PREPARED -> ANSWERING -> AUTO_SUBMITTING -> SUBMITTED
      |
      +-------------------------------------> CANCELLED (当前 ExamTerminated 只覆盖未开考)
  ANSWERING -- ExamTerminated --> [当前无状态迁移，缺陷]

submission_timeout_task:
  WAITING -> PENDING -> PROCESSING -> DONE / FAILED
      |         |
      +---------+------------------> CANCELLED
```

## 5. 缺陷根因、影响与修复建议

### E-01 P0：开关与路由语义分裂，默认兼容入口绕过容量保护

**证据链**

- 前端 V2 默认开；Runtime/Compose V2 默认关。
- 前端只对 `EXAM_ENTRY_V2_DISABLED` 和 404 回退 `/start`。
- `/start` 在存在本地投影时调用 `legacyStart`。
- `legacyStart` 仍执行 prepare/activate/delivery，但激活显式传入 `enforceSlot=false`。
- [`ExamEntryRateLimitFilter.java`](../services/exam-gateway/src/main/java/com/ekusys/exam/gateway/ExamEntryRateLimitFilter.java) 正则只匹配 `entry/prepare|entry/activate|paper-delivery`，不匹配 `/start`。

**影响**

- 开考瞬间所有兼容客户端可直接执行激活和大试卷回包，绕过稳定 slot 和入场令牌桶。
- 运维人员看到“V2=false”容易误判当前是纯旧链路。
- 三段 API 指标不能完整反映真实入场流量。

**修复建议**

1. 立即将 `/start` 纳入 Gateway 单独的 `legacy-start` 限流和 Runtime 指标，其容量应按“激活 + 试卷大回包”而不是普通 API 评估。
2. 将开关改为明确模式，例如 `app.exam-entry.mode=LEGACY_DYNAMIC|V2_COMPAT|V2_SPLIT`，并为每种模式建立路由矩阵集成测试。
3. 发布时将前端开关和 Runtime 模式作为一个受控发布单元，不要依赖两个相反默认值自动协调。
4. 完成 V2 压测后，目标生产流程应显式使用 `V2_SPLIT`；`/start` 只作为受限、可观测、有退役日期的兼容入口。

### E-02 P0：草稿版本与设备时钟耦合，可静默丢失答案

**证据链**

- `PaperDeliveryView` 已返回 `draftVersion`。
- 前端选择草稿时比较 `localDraft.updatedAt` 和 `serverDraftTime`，前者来自浏览器，后者来自服务端。
- 前端初始化 `syncState.snapshotVersion` 时只使用本地值，没有与 `delivered.draftVersion` 取最大值。
- 快照版本由 `Date.now()` 生成；Redis Lua 只接受更大版本，旧版本返回负的当前版本，但 `ExamSnapshotService` 对其取绝对值后以普通 ACK 返回，客户端无法区分“已写入”和“因版本旧而未写入”。

**典型失败场景**

1. 设备 A 时钟偏快，保存了较大的版本。学生换到时钟正常或偏慢的设备 B，B 的新答案版本可能不大于服务端版本。
2. Redis 拒绝覆盖，返回已存版本。
3. 前端更新本地 ACK 和版本，并可将 `dirty` 清除，但 B 的新答案未进入服务端快照。

**修复建议**

1. 停止使用客户端 epoch 毫秒作为权威版本。由 Runtime 为每个 Session 分配单调 revision，客户端提交 `baseVersion + clientMutationId + answers`。
2. 服务端 ACK 显式返回 `accepted=true/false`、`storedVersion`和冲突原因；旧版本不得伪装成成功写入。
3. 前端恢复时首先比较 server revision 与本地 `lastAcknowledgedServerVersion`；本地未同步变更使用独立的 local sequence，不再比较设备时钟。
4. 对“服务端和本地都有未合并更改”返回明确冲突，保留两份草稿和可审计的用户选择，不做静默覆盖。

### E-03 P0/P1：激活、租约和试卷交付之间存在计时公平性窗口

**证据链**

- 试卷缓存在激活事务前被读取一次，这避免了“已知试卷不可用仍开始计时”。
- 但 MySQL 事务一旦提交，Session 和 deadline 已确定；随后的 Redis 租约激活、HTTP 响应、第二次缓存读取和大试卷回包都可失败。
- `first_paper_delivered_at` 在 Controller 完成响应之前就被写入，无法证明客户端已收到试卷。

**修复建议**

1. 引入有 TTL 的 `ACTIVATING` 两阶段状态：第一阶段预留租约和交付凭证，但不开始正式作答计时；客户端完成试卷验证后发送确认。
2. 为防止客户端故意不确认，deadline 可定义为 `min(confirmAt, reservedAt + shortGrace) + duration`，并且仍不超过全局考试结束时间。
3. 记录 `activation_reserved_at`、`paper_response_started_at`、`client_confirmed_at`及它们的差值，对超过阈值的会话主动告警和补偿，而不是仅记录一个服务端首次调用时间。
4. 若暂时不改状态机，至少要在交付失败时保持原租约可幂等恢复，延长前端重试窗口，并按“已激活但未确认交付”建立专项监控。

### E-04 P0：终止考试没有停止正在作答的会话

**证据链**

- [`ExamProvisioningService.java`](../services/exam-runtime-service/src/main/java/com/ekusys/exam/runtime/entry/ExamProvisioningService.java) 收到 `ExamTerminated` 后会先把 `runtime_exam_definition` 更新为 `TERMINATED`。
- 同一方法后续只取消 `s.status='PREPARED'` 对应的 `WAITING` Timeout Task、`IN_PROGRESS` Submission 和 Session；没有处理 `ANSWERING` Session、`PENDING` Timeout Task 或 Redis 租约。
- 新的 `prepare/activate` 会因考试已终止而拒绝入场，但已有会话的 heartbeat、snapshot 和交卷路径只校验 Session/租约，没有以考试投影的 `TERMINATED` 状态阻断。
- 现有终止测试覆盖事件路由和“终止压过后到的发布重放”，没有覆盖终止时已经存在 `ANSWERING` 会话的状态收敛。

**影响**

- 教师界面显示考试已终止后，已进入考试的学生仍可继续作答和提交，管理端状态与 Runtime 事实不一致。
- 超时任务仍会在原 deadline 触发，导致一次终止命令之后继续产生快照、交卷和成绩事件。
- 如果简单补一条 `ANSWERING -> CANCELLED` SQL，又会丢弃学生已经作答的答案，因此不能仅扩大当前更新条件。

**修复建议**

1. 明确终止策略：建议“未开考会话取消，正在作答会话强制交卷并保留最新服务端草稿，已提交会话幂等忽略”。如果产品要直接作废，也必须把成绩、审计和学生提示语义写入契约。
2. 对正在作答的会话执行持久化、幂等的终止任务：条件更新 `ANSWERING -> AUTO_SUBMITTING`，复用或扩展自动交卷协调器，以 `source=EXAM_TERMINATED` 固化最新草稿、写 `SubmissionAccepted`/状态事件，再在事务提交后清理租约。
3. 不要在一条 `ExamTerminated` 消费事务中同步处理数千个学生。先落本地终止批次和任务，分批抢占、重试并记录完成数；重复事件和实例重启后应继续收敛。
4. 状态迁移开始后，heartbeat、snapshot 和手工 submit 必须与终止任务使用同一状态机和条件更新裁决，避免与最后一次快照、手工交卷、超时交卷并发时重复或漏交。
5. 增加“开考前终止、作答中终止、终止与手工交卷/快照/超时并发、重复终止事件、多实例接管”的 MySQL/Redis 集成测试，并将终止完成数和失败数纳入教师端及告警。

### E-05 P1：重试时间算法会过早重试

当前算法核心是：

```text
ceiling = min(exponentialBackoffCap, serverRetryAfterMs)
delay = random(0, ceiling)
```

`Retry-After` 的语义应是“在此之前不要重试”，而当前实现把它当作上限。建议改为：

```text
delay = serverRetryAfterMs + random(0, boundedJitter)
```

如服务端未返回建议时间，再使用带 full jitter 的指数退避。前端与 [`exam-entry-10000.js`](../deploy/load-test/exam-entry-10000.js) 必须同步修正，否则压测脚本本身会放大被测系统的重试流量。

### E-06 P1：Runtime 准备状态没有进入学生/教师业务闭环

**问题**

- Management 发布事务成功即返回，Runtime 预创建和预热是后续最终一致流程。
- 学生列表仅看 Management `PUBLISHED`，不知道 Runtime 是 `PROVISIONING`、`FAILED` 还是 `READY`。
- 失败后的修复主要依赖指标、DLQ 和内部 reconcile 接口，学生只看到通用重试文案。

**建议**

1. Runtime 在自己的预创建事务完成后，通过 Runtime Outbox 发出 `ExamRuntimePrepared`/`ExamRuntimePreparationFailed`。
2. Management 或 Reporting 幂等投影该状态，学生列表返回 `entryReadiness`；教师页面显示冻结人数、预创建人数、缓存预热和失败原因。
3. 只有 `READY` 时显示正常入场；`PROVISIONING` 显示候场进度而不是在页面内盲目重试 30 秒。
4. 保持跨服务“至少一次 + 幂等投影”，不要为了同步状态直接读 Runtime Schema 或引入分布式事务。

### E-07 P1：考前检测只在前端生效

**问题**

- 直接路由可绕过弹窗，同时 Runtime `prepare/activate` 不接收任何检测挑战或结果。
- 浏览器中的摄像头、多屏和屏幕共享检测可以改善合规体验，但不能被表述为不可伪造的安全保证。

**建议**

1. 在 Frontend 路由守卫中要求当前考试的一次性 precheck 状态，防止普通用户误绕过；这仍只是 UX 保护。
2. Runtime `prepare` 签发短时 precheck challenge，前端上报结果、客户端能力和必要审计记录，`activate` 按监考策略校验 challenge 是否完成。
3. 明确文档化 Web 检测的信任边界；若业务需要强防作弊，必须使用受控客户端/安全浏览器及服务端可验证证据，不能只增加 JavaScript 检查。

### E-08 P1：万人发布事件过大，Reporting 存在 20,000 次单行写

**问题**

- Management 将每名学生的 `studentId/classId/className` 放在一条 `ExamPublished` 中。
- Runtime 只使用 `studentId`，Reporting 使用班级信息，两个不同消费模型被耦合在同一大载荷中。
- Reporting `projectExam` 先删除旧投影，再对每个 candidate 分别写 `rpt_exam_candidate` 和 `rpt_proctoring_student`，全部位于一个消费事务。

**建议**

1. 将元数据事件与考生快照分开：`ExamPublished` 只携带考试和快照元数据，考生使用有 `snapshotId/batchIndex/batchCount/candidateCount/checksum` 的分片事件。
2. Runtime 和 Reporting 使用 `inbox_event + snapshotId + batchIndex` 幂等消费，只有全部分片数量与 checksum 一致时才将考试改为 `READY`。
3. Reporting 使用 JDBC `batchUpdate` 或 staging table + 集合 SQL，避免 20,000 次网络/驱动层往返。
4. 这是公共事件变更，发布顺序必须是：先上线兼容新旧格式的 Runtime/Reporting 消费者，再上线 Management 生产者，最后停止旧格式。

### E-09 P1/P2：时间权威不一致

**问题**

- V2 `prepare/activate/paper-delivery` 使用 DB 时间，这是正确方向。
- `ExamRuntimeService.heartbeat` 和 `snapshot` 使用 JVM 时间；Redis Lua 租约续期也使用该时间参数。
- Frontend 的列表可进入判断、草稿版本和部分恢复判断使用浏览器时间。

**建议**

1. 所有改变会话可接受性、deadline 和租约权威状态的 SQL 都使用 `current_timestamp(3)`。
2. Redis 租约 Lua 使用 Redis `TIME`，不相信应用节点或浏览器传入的当前时间。
3. 浏览器倒计时继续使用服务端 deadline，只作展示；服务端始终在心跳、快照和交卷时重新裁决。

### E-10 P2：候场窗口在前端硬编码为 10 分钟

Runtime 已支持 `APP_EXAM_ENTRY_WAITING_ROOM_MINUTES`，但 [`ExamList.vue`](../src/main/resources/frontend/src/views/student/ExamList.vue) 固定使用 10 分钟。配置改大时前端会过晚开放，配置改小时会过早开放并由后端拒绝。

建议由学生考试摘要直接返回 `entryOpensAt` 和 `serverTime`，前端只展示服务端结果，不复制后端配置规则。

### E-11 P2：reconcile 不是可重复的对账修复

`ExamProvisioningReconcileService` 用 `examId + paperSnapshotVersion` 生成确定性 eventId。第一次 reconcile 完成并写入 `inbox_event` 后，同一快照的后续数据漂移再调 reconcile 会因“已处理”直接返回，不会重新核对和补齐。

建议将“消息重放幂等”和“人工对账命令”分开：后者每次产生新的 `commandId`，记录操作人、对账前后计数、修复项和结果，并保证只做可证明安全的补齐，不静默删除正在作答的会话。

### E-12 P2：可观测性和测试仍有缺口

**可观测缺口**

- `/start` 兼容入场不在 Gateway 入场限流的分类和拒绝指标中。
- `exam.entry.lifecycle.dlq` 是进程内计数器，实例重启会归零，不等于 RabbitMQ DLQ 的实际深度。
- 没有“激活成功到客户端确认试卷交付”的端到端延迟和失败数。
- 当前 `pendingCandidates` 进程内值会被并发预创建任务相互覆盖，虽然 10 秒的 DB 刷新会最终校正。

**测试缺口**

- 已有用例证明 100 个并发请求激活同一 Session 时只有一次真正开始，也证明 40 名不同学生不共享行锁。
- 但没有一个端到端测试覆盖“前端开关×Runtime 开关×投影状态”路由矩阵。
- 没有测试“MySQL 激活已提交，Redis 租约或试卷回包失败”时学生损失的计时和恢复行为。
- 没有跨设备时钟偏差、服务端草稿更新和 stale ACK 的数据不丢失测试。
- 没有覆盖 `ANSWERING` 会话收到 `ExamTerminated` 后强制停止、保留答案并与手工/超时交卷幂等收敛的测试。
- 仓库提供了万人 k6 脚本，但本次和仓库记录都不能证明它已在目标容量与故障注入场景下通过。

## 6. 建议的目标流程

### 6.1 发布前

1. Management 冻结试卷和名册，产生考试元数据事件和带批次/校验和的考生快照分片。
2. Runtime/Reporting 幂等消费全部分片；Runtime 预创建数据并预热试卷。
3. Runtime 在本地事务完成后发出 `ExamRuntimePrepared`；Management/Reporting 投影准备状态。
4. 教师在页面看到 `READY` 和人数校验后，才把本场考试视为可开考。

### 6.2 学生入场

1. 列表返回 `serverTime`、`entryOpensAt`、`entryReadiness`和作业策略；前端不再硬编码 10 分钟。
2. `prepare` 签发与考生、客户端、slot 和 precheck challenge 绑定的候场票据。
3. 客户端完成考前检测并提交 challenge；服务端保留结果与信任边界记录。
4. `activate` 先创建有短 TTL 的 `ACTIVATING` 预留和租约，返回可验证的试卷交付凭证。
5. 客户端获取并校验快照后发送 confirm；Runtime 使用 DB 时间将 Session 改为 `ANSWERING`、计算 deadline、启用超时任务并写 `SessionStarted` Outbox。
6. 超过短宽限仍未 confirm 时，按服务端规则开始计时或取消预留，防止客户端利用确认步骤延迟开考。

### 6.3 恢复作答

1. Runtime 返回权威 `serverDraftVersion`和答案。
2. IndexedDB 保存 `lastAcknowledgedServerVersion`、本地未同步 mutation 列表和 idempotency key，不使用设备时间判断先后。
3. 服务端对 `baseVersion` 做 CAS；冲突时返回可操作的冲突结果，不返回伪成功 ACK。

## 7. 分阶段修复与发布顺序

### 阶段 0：大考上线前必须完成

1. 补齐 `/start` 限流、指标和开关路由矩阵测试；明确目标环境最终模式。

5. 至少建立“激活已开始但试卷未确认交付”监控、告警和人工补偿规则；更优方案是上线 `ACTIVATING` 两阶段状态。
6. 在隔离环境完成 10,000 人三段式压测、双设备冲突、考试终止、Redis/Content/MySQL 故障注入和恢复测试。

1. 引入 Runtime 准备完成/失败事件和学生/教师可见投影。

### 建议发布顺序

1. Gateway：先增加 `/start` 保护，不改变业务契约。
2. Reporting：先兼容新的准备事件和分片候选事件。
3. Runtime：上线新模式开关、草稿版本协议、新状态机和准备完成 Outbox，保持对旧前端的兼容窗口。
4. Management：上线新事件生产和准备状态投影。
5. Frontend：最后打开新流程，并在渐进流量下观察完整链路指标。
6. 稳定后停止旧事件格式和 `/start` 兼容流量。

## 9. 上线准入清单

在宣称“万人入场可上线”前，建议至少满足：

- [ ] 目标环境的前端/Runtime 入场模式一致，`/start` 有独立保护或已无流量。
- [ ] 草稿使用服务端单调版本，stale 写入不返回伪成功，跨设备时钟偏差测试通过。
- [ ] 激活到客户端确认试卷的计时公平性已解决，或已有明确补偿与审计。
- [ ] 考试终止能使 `PREPARED` 会话取消、`ANSWERING` 会话保留答案后强制交卷，并与手工/超时交卷幂等收敛。
- [ ] 客户端严格遵守 `Retry-After`，不在限流窗口恢复前循环请求。
- [ ] Runtime 准备状态对教师和学生可见，`FAILED`/DLQ 有告警、处置人和可审计重放。
- [ ] 10,000 人压测达到仓库脚本阈值，且同时采集 Hikari、MySQL CPU/IO/Redo/锁等待、Redis 延迟、RabbitMQ/Outbox 积压和应用 GC。
- [ ] 完成 Redis 故障、Content 超时、RabbitMQ 积压、Runtime 实例重启和 MySQL 慢/主从切换故障注入。
- [ ] 核对 Session、Submission、Timeout Task 数量等于冻结考生数，每个已激活 Session 只有一个确定性 `SessionStarted`。
- [ ] 明确公共事件的消费者先行、生产者后行发布顺序，并保留回退边界。

## 10. 最终评价

当前 Exam Entry V2 不是一个需要推倒重来的方案。它已经解决了旧入场流程最核心的几个架构问题：名册和会话提前准备、不在开考高峰为每个学生跨服务拉取完整试卷、用行级条件更新保证幂等激活、用服务端租约保证单活，以及把超时任务与个人 deadline 同事务启用。

它当前的主要风险集中在“最后一公里”：默认配置没有真正走目标流程、个人计时与交付成功之间存在窗口、草稿版本仍相信客户端时钟、终止考试不能停止正在作答的会话，以及准备状态和容量结论没有进入业务闭环。应按本文的 P0 顺序先修正数据正确性、生命周期闭环和流量路由，再通过真实容量和故障注入证明可上线性。
