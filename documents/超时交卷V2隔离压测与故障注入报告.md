# 超时交卷 V2 隔离压测与故障注入报告

## 结论

截至 2026-09-03，仍不能开启 `APP_TIMEOUT_SUBMISSION_V2_ENABLED`。正确性场景均能最终收敛，并已将默认租约从 60 秒缩短为 30 秒，但数据库主草稿的 10,000 人公平复测仍未通过容量闸门：

- 历史 2、4 实例 10,000 人基线零遗漏，但当时使用 Redis 兼容回退，数据库 P99 均约 63 秒。
- 2026-09-03 数据库主草稿复测中，2 实例 P99 `54.203s`，4 实例 P99 `39.531s`，均未达到 `<30s`。
- 全新数据卷下的 4 实例最终公平复测为 10,000/10,000，数据库 P99 `47.021s`、最大 `47.282s`；零遗漏与 `<60s` 通过，`<30s` P99 失败。
- 命中执行窗口后杀死一个 Runtime，8 条已领取任务只能等待 60 秒租约过期，数据库最大完成时间约 63.8 秒。
- Redis、RabbitMQ、XXL-Job 和 MySQL 的有界故障验证均最终零遗漏；其中 RabbitMQ 中断不阻塞 Runtime 最终事务，恢复后 Outbox 全部发布。

因此发布闸门保持关闭。30 秒租约已为实例退出恢复留出 `<60s` 的理论余量，但本轮基线未通过，因此没有将新租约下的故障矩阵误标为有效上线证据。

## 环境与口径

- 日期：2026-09-02 至 2026-09-03（Asia/Shanghai）
- 主机：16 vCPU、约 30 GiB 内存
- 隔离 Compose 项目：`exam-platform-cloud-timeout`
- 隔离网络：`exam-cloud-timeout`
- 隔离数据卷：`exam-platform-cloud-timeout-*`
- Runtime：JDK 21，V2 仅由隔离覆盖文件开启
- 2026-09-02 历史场景配置：`worker-count=8`、`batch-size=8`、`task-timeout-ms=20000`、`lease-ms=60000`、`lease-renew-interval-ms=15000`、`max-run-ms=25000`
- 2026-09-03 复测配置：`worker-count=8`、`batch-size=8`、`task-timeout-ms=20000`、`lease-ms=30000`、`lease-renew-interval-ms=10000`、`max-run-ms=25000`；主配置 V2 仍为 `false`
- 草稿：每人约 100 题、约 100 KB；有界故障场景中 `submission_draft_payload` 使用 `GZIP_JSON_V1` 与 SHA-256，Redis 保留兼容副本
- 权威延迟：MySQL `submission_timeout_task.due_at -> completed_at`
- 客户端观察：历史 k6 使用 1.5 秒指数退避、上限 5 秒；2026-09-03 起为截止后首次请求也加入带抖动的退避，基础 3 秒、上限 10 秒

压测工具与所有服务运行在同一台主机，因此结果只能作为当前隔离环境的上线闸门证据，不能外推为生产容量。采样期间曾观察到单个 Runtime 约 250%～310% CPU、Gateway 约 400% CPU、MySQL 约 210% CPU；本轮没有完整的时序资源曲线，资源报告闸门仍不完整。

两轮均无永久 `FAILED`、无最终载荷遗漏。4 实例并未优于 2 实例，说明当前瓶颈不是简单增加 Runtime 副本即可消除；Gateway 状态轮询与 MySQL 竞争也会影响同机结果。

证据限制：这两轮 10,000 人基线是在夹具补写 `submission_draft_payload` 之前执行，使用的是 Redis 旧数据兼容回退。后续故障场景才验证数据库主草稿。因此这些历史结果足以否决当时的上线闸门，但不能作为数据库主草稿路径的容量结论；主草稿的独立复测结果见下节。

此前在 4 实例基线中定位并修复两类额外问题：

1. 自动 reconciliation 使用 `INSERT ... SELECT` 持有大量 `exam_session` 二级索引共享锁，与最终化更新形成死锁。现改为只读计数和告警，符合“不自动伪造最终结果”的约束；复测死锁日志为 0。
2. 执行器拒绝或 job 总预算耗尽后，已领取任务原本会等待完整租约。现增加单实例防重入，并按当前 token 立即将未完成任务转入有界重试；复测无线程拒绝遗留任务。

## 未通过闸门与下一步

1. 优化 Runtime 最终化热路径的数据库 I/O 与事务持锁时间；在无状态查询时 P99 仍为 `31.102s`，不能只把瓶颈归因于 Gateway 轮询。
2. 将状态读容量与最终化写容量分开评估，可考虑只读投影或受控缓存，但最终回执仍必须以 Runtime 权威状态为准，不得用客户端推测代替。
3. 先建立 MySQL 全局连接预算，覆盖 Gateway 后所有服务与运维余量；不得在未提高或分离数据库容量时盲目增大 Runtime Hikari 和工作线程。
4. 分离负载发生器、Gateway、Runtime 和 MySQL 主机，补采 Hikari、MySQL CPU/IO/Redo/锁等待、Redis 延迟、任务积压和 Outbox 积压的完整时序，再重跑全新的 2、4 实例数据库主草稿基线。
5. 基线通过后，重跑 30 秒租约下的 Runtime 退出以及 Redis、MySQL、RabbitMQ、XXL-Job 完整故障矩阵，并验证真实告警送达。

在这些条件全部满足前，主配置与运维发布步骤必须继续保持 V2 关闭。
