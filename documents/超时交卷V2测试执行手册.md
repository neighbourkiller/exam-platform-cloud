# 超时交卷 V2 测试执行手册

> 适用仓库：EkuExam Cloud
>
> 适用范围：Runtime 答题快照、手工交卷、超时自动交卷、Outbox、Reporting 投影和学生端交卷状态
>
> 文档基线：2026-09-12 当前工作区
>
> 默认结论：在全部上线闸门通过前，`APP_TIMEOUT_SUBMISSION_V2_ENABLED` 必须保持 `false`

## 执行总览

一次完整测试按以下顺序推进，前一阶段失败时停止放行判断，但保留失败证据：

1. 固定 Git commit、工作区差异、待测镜像和配置基线；
2. 检查 JDK、Docker、Node、端口、磁盘和机密配置；
3. 执行 Runtime、Outbox、Reporting 和前端自动化测试；
4. 构建当前源码的隔离 Runtime 镜像并拉起 Compose 环境；
5. 执行快照、时钟、并发交卷、永久失败、重放和终止业务矩阵；
6. 依次执行 2 实例、4 实例的纯后台、状态查询和截止交卷容量场景；
7. 在独立轮次执行 Runtime、Redis、MySQL、RabbitMQ、XXL-Job 故障注入；
8. 汇总数据库权威结果、客户端结果、资源曲线、消息收敛和告警送达证据；
9. 对照所有闸门决定保持关闭、继续整改或进入小流量开启；
10. 保存不含机密的报告并清理隔离环境。

## 1. 测试目标与可靠性边界

本手册用于验证从“截止前最后一次答案快照”到“Runtime 完成最终交卷事务”的完整链路：

```text
浏览器 IndexedDB / 快照请求
  -> Runtime 数据库草稿栅栏
  -> submission_timeout_task
  -> XXL-Job 唤醒 examTimeoutSubmitJob
  -> 多 Runtime 按任务租约领取
  -> 最终答案 + Session + Submission + Task + Outbox 同事务提交
  -> RabbitMQ 至少一次投递
  -> Grading / Reporting 幂等消费
  -> 学生端查询交卷回执
```

SLA 的截止点是 Runtime 本地事务完成，即
`submission_timeout_task.due_at -> completed_at`。RabbitMQ Confirm、自动判分和 Reporting
投影属于事务外的最终一致链路，不计入 Runtime 的 30/60 秒 SLA，但必须单独验证最终收敛和幂等性。

放行目标如下：

- 10,000 个同一 `due_at` 的任务零遗漏；
- 数据库权威完成延迟 P99 `<30s`，最大值 `<60s`；
- 60 秒内任务完成率 100%；
- Task、Session、Submission、最终载荷和逻辑 Outbox 数量一致；
- `FAILED=0`，测试结束后长期 `PROCESSING=0`；
- 重试任务数量不超过总任务数的 0.5%；
- 故障注入后旧租约令牌不能覆盖新结果；
- Reporting 不被迟到或重放事件从 `GRADED` 降级；
- 学生端只有收到 `RUNTIME_FINALIZED` 或 `runtimeFinalized=true` 才清理本地草稿；
- 监控告警真实送达，而不只是指标存在。

## 2. 两级测试环境

### 2.1 仓库隔离 Compose 环境

仓库自动化套件使用以下两个 Compose 文件叠加：

```text
docker-compose.yml
deploy/load-test/compose.timeout-test.yaml
```

测试项目固定为 `exam-platform-cloud-timeout`，使用独立网络 `exam-cloud-timeout` 和以下独立卷：

- `exam-platform-cloud-timeout-mysql-data`
- `exam-platform-cloud-timeout-redis-data`
- `exam-platform-cloud-timeout-rabbitmq-data`
- `exam-platform-cloud-timeout-minio-data`
- `exam-platform-cloud-timeout-jwt-keys`

该环境适合功能回归、集成测试、脚本验证和同机性能诊断。虽然数据卷和网络与普通开发环境隔离，
但 Gateway、Runtime、MySQL、Redis、RabbitMQ、XXL-Job 和负载发生器仍可能共享一台宿主机的
CPU、内存和磁盘，因此不能把同机结果直接外推为生产容量。

### 2.2 上线前资源分离环境

最终容量证明应至少做到：

- k6 负载发生器与服务集群分离；
- MySQL 使用独立主机或独立、可观测的存储资源；
- Redis、RabbitMQ 不与 MySQL 争用同一磁盘；
- 2 个和 4 个 Runtime 实例使用同一待发布镜像；
- 采集 Runtime Hikari、JVM、MySQL CPU/IO/Redo/fsync、Redis 延迟、RabbitMQ 和 XXL-Job 指标；
- 每个故障场景独立执行，禁止在一轮结果中叠加多个故障后仍宣称单项通过。

如果只有单机 Compose 环境，可以完成代码正确性和回归测试，但上线结论必须写成“尚未完成资源分离容量验收”。

当前 `run-timeout-suite.sh` 会直接操作本机 Compose、`localhost:16730` 和本机测试卷，不能仅通过
修改一个 URL 就变成资源分离测试。资源分离环境需要使用同一镜像和同一 k6 脚本，另外提供经过评审的
远端部署、数据准备与安全令牌分发流程；在该流程落地前，不得把本机套件标记为资源分离验收。

## 5. 建立隔离 Compose 环境

### 5.1 检查端口冲突

测试覆盖环境沿用基础 Compose 的宿主机端口，例如 Gateway `16730`、MySQL `23306`、
Redis `26379`。同一宿主机上不要同时运行占用这些端口的普通项目。

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices config --services
```

`config --services` 只用于检查服务清单。不要把完整 `docker compose config` 输出保存到报告，
因为展开后的环境可能包含机密。

### 5.2 启动基础隔离环境

压测覆盖使用的 Dockerfile 读取当前 Runtime JAR。首次建立环境时，先完成打包和镜像构建：

```bash
JAVA_HOME=<JDK21目录> bash ./mvnw \
  -pl services/exam-runtime-service -am package -DskipTests

mkdir -p deploy/load-test/.runtime-image
cp services/exam-runtime-service/target/exam-runtime-service-1.0.0-SNAPSHOT.jar \
  deploy/load-test/.runtime-image/app.jar

docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices \
  build runtime-service

rm deploy/load-test/.runtime-image/app.jar
rmdir deploy/load-test/.runtime-image
```

确认上一步镜像构建成功后，再启动 4 个 Runtime：

```bash
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices \
  up -d --scale runtime-service=4
```

正式容量场景优先由 `run-timeout-suite.sh` 构建当前源码镜像并启动环境，不要先手工构建另一份镜像。

### 5.3 验证启动状态

```bash
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices ps

curl --fail http://localhost:16730/actuator/health
```

随后检查过滤后的 Runtime 日志：

```bash
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices \
  logs --no-color runtime-service \
  | grep -E 'Started|Timeout submission initialized|Flyway|ERROR'
```

必须确认：

- MySQL、Redis、RabbitMQ、Nacos、XXL-Job 和 Gateway 健康；
- Runtime 实例数量符合场景；
- 所有 Runtime 使用同一镜像 ID；
- Runtime Flyway 已成功应用；
- 隔离 Runtime 的超时交卷 V2 已开启；
- 没有 `Too many connections`、迁移失败或消息拓扑失败。

仅看到容器状态为 `running` 不等于业务环境可用。

## 6. 代码级和模块级验证

容量压测前必须先通过确定性更高的单元测试和集成测试。

### 6.1 Runtime 与平台依赖

```bash
JAVA_HOME=<JDK21目录> bash ./mvnw \
  -pl services/exam-runtime-service -am test
```

该命令应覆盖：

- 数据库时间判断；
- 快照客户端序列与服务端版本；
- 数据库主草稿和 SHA-256；
- 手工交卷与超时任务接管；
- 任务领取、租约续期、过期令牌和硬预算；
- 永久失败与重放前置条件；
- Redis 重启后的快照队列恢复；
- Outbox 租约和批量发布状态更新；
- 真实 MySQL 闩锁、迁移和事务测试。

以 Maven 最终的 `BUILD SUCCESS`、Tests run、Failures 和 Errors 汇总为准。普通 Spring、Mockito、
Flyway 新版本提示不能单独判为失败。

### 6.2 Reporting 投影

```bash
JAVA_HOME=<JDK21目录> bash ./mvnw \
  -pl services/exam-reporting-service -am test
```

重点确认：

- 新旧 `SubmissionAccepted` 事件均可消费；
- 新增字段缺失时兼容；
- 重复事件幂等；
- `GRADED` 不被迟到或重放的 `SubmissionAccepted` 降级为 `PROCESSING`；
- Flyway V6 能从空 Schema 正常迁移。

### 6.3 前端状态机

```bash
cd src/main/resources/frontend
npm ci
npm test
npm run test:submission-flow
npm run test:exam-entry
npm run build
cd ../../../..
```

超时交卷前端测试至少覆盖：

- `SUBMITTING -> RUNTIME_FINALIZED`；
- `SUBMITTING -> FAILED`；
- 截止后的本地答案不继续静默重试；
- 浏览器时钟偏差和服务器时钟校正；
- 刷新后从 IndexedDB 恢复；
- 旧响应不能覆盖更高 `serverRevision`；
- 只有 Runtime 最终完成才清理草稿；
- 7 天申诉证据到期清理。

Vite 的大 chunk 警告需要记录，但在构建退出码为 0 时不等同于本次功能测试失败。

### 6.4 文件和迁移检查

```bash
bash -n deploy/load-test/run-timeout-suite.sh
node --check deploy/load-test/prepare-timeout-load-data.mjs
node --check deploy/load-test/timeout-submission.js
git diff --check
```

还要人工确认：

- Runtime 新迁移只增加版本，没有修改旧迁移；
- Reporting 新迁移位于 Reporting 服务自己的 Schema；
- 没有提交 `target/`、前端 `dist/`、令牌文件或测试答案；
- 没有夹带 `.gitignore`、简历模板等无关修改。

## 7. 业务正确性测试矩阵

模块测试通过后，再执行以下业务矩阵。每一项都应记录测试数据、开始时间、预期、实际结果和证据位置。

| 编号 | 场景 | 关键断言 |
|---|---|---|
| F-01 | 截止前快照事务先提交 | 该版本进入最终载荷 |
| F-02 | 超时任务先把 Session 改为 `AUTO_SUBMITTING` | 随后到达的快照被拒绝 |
| F-03 | 重试相同 `clientSequence` | 不生成新的 `serverRevision` |
| F-04 | 旧响应晚于新响应到达浏览器 | 前端保留较高服务端版本 |
| F-05 | JVM 与 MySQL 时间偏差正负 30 秒 | 最终截止判断以数据库时间为准 |
| F-06 | 浏览器时间偏差正负 5 分钟和高 RTT | 倒计时经服务器时间校正 |
| F-07 | 手工交卷与超时任务并发 | 只产生一个最终载荷和一个逻辑事件 |
| F-08 | 达到最大重试次数 | Task=`FAILED`、Session=`SUBMISSION_FAILED` |
| F-09 | 无权限、重复或已有最终结果时重放 | 重放接口拒绝且留下审计记录 |
| F-10 | 合法重放 | 只恢复当前任务并增加 `replay_count` |
| F-11 | 终止 PREPARED/WAITING 考试 | 会话取消，不伪造交卷结果 |
| F-12 | 终止 ANSWERING 考试 | 截止时间加速，仍由正常超时链路固化答案 |
| F-13 | 终止与快照/手工交卷并发 | 状态机和最终载荷保持幂等 |
| F-14 | Reporting 收到重复、乱序事件 | 投影单调更新，不发生状态降级 |
| F-15 | 离线跨越截止时间后恢复 | 未接受答案保留为申诉证据，不再自动提交 |

快照并发边界应使用真实 MySQL 闩锁控制事务顺序，不能用线程 `sleep` 推测先后关系。

## 8. 10,000 人容量测试

### 8.1 套件参数

```text
bash deploy/load-test/run-timeout-suite.sh <场景名> <Runtime副本数> <每实例工作线程数> <MySQL最大连接数>
```

常用环境变量：

| 变量 | 默认值 | 用途 |
|---|---:|---|
| `USERS` | `10000` | 会话数量 |
| `EXAM_ID` | `99000001` | 本轮唯一考试 ID |
| `DUE_SECONDS` | `60` | 数据准备完成后距截止时间 |
| `ENABLE_POLLING` | `true` | 是否执行 k6 客户端场景 |
| `LOAD_FLOW` | `status_only` | `status_only` 或 `deadline_submit` |
| `BUILD_RUNTIME_IMAGE` | `true` | 是否从当前工作区重建 Runtime 镜像 |
| `POLL_BASE_MS` | `3000` | 首次/基础轮询间隔 |
| `POLL_MAX_MS` | `10000` | 最大轮询间隔 |
| `FAULT_INJECTION` | `none` | 当前自动支持 `none`、`node_crash` |
| `APP_RUNTIME_DB_MAX_POOL_SIZE` | `24` | 每个 Runtime Hikari 最大连接数 |

每轮必须使用新的 `EXAM_ID` 和可辨识的场景名。不要用相同考试 ID 并发执行两个套件。

### 8.2 数据准备逻辑

套件会自动：

1. 使用 JDK 21 打包当前 Runtime；
2. 将当前 JAR 放入压测专用镜像；
3. 拉起指定数量的 Runtime；
4. 清理隔离 Redis DB 1，并重置 MySQL 状态计数和 SQL digest；
5. 生成 10,000 个仅供本轮使用的学生 JWT；
6. 写入约 100 题、100 KB 的 Redis 兼容草稿；
7. 写入相同内容的 `GZIP_JSON_V1` 数据库主草稿及 SHA-256；
8. 先使用远期截止时间完成装载，再原子切换为本轮真实截止时间；
9. 启动容器资源采样和 k6；
10. 在截止后 30 秒、60 秒采集完成数并执行自动闸门。

临时令牌文件会在脚本退出时删除。报告不得包含 JWT、答案明文或私钥。

### 8.3 首轮构建与后续复用

第一轮应从当前源码构建镜像：

```bash
JAVA_HOME=<JDK21目录> \
EXAM_ID=99100001 \
LOAD_FLOW=status_only \
bash deploy/load-test/run-timeout-suite.sh BASELINE-2X8-STATUS 2 8 300
```

只有确认源码未变化且需要连续执行对照场景时，后续轮次才可复用该镜像：

```bash
JAVA_HOME=<JDK21目录> \
BUILD_RUNTIME_IMAGE=false \
EXAM_ID=99100002 \
LOAD_FLOW=status_only \
bash deploy/load-test/run-timeout-suite.sh BASELINE-4X8-STATUS 4 8 300
```

`metadata.json` 中必须记录相同 `runtimeImageId`。如果源码、依赖、配置或迁移发生变化，必须重新构建。

### 8.4 必跑基线矩阵

按下列顺序执行，每轮使用不同 `EXAM_ID`：

| 顺序 | Runtime | 客户端流程 | 用途 |
|---:|---:|---|---|
| 1 | 2×8 | 无轮询 | 测量纯后台最终化能力，诊断项 |
| 2 | 2×8 | `status_only` | 验证刷新/恢复后的状态查询 |
| 3 | 2×8 | `deadline_submit` | 验证截止时交卷接管协议 |
| 4 | 4×8 | 无轮询 | 测量扩容后的纯后台能力，诊断项 |
| 5 | 4×8 | `status_only` | 正式放行场景 |
| 6 | 4×8 | `deadline_submit` | 正式放行场景 |

纯后台命令示例：

```bash
JAVA_HOME=<JDK21目录> \
BUILD_RUNTIME_IMAGE=false \
ENABLE_POLLING=false \
EXAM_ID=99100003 \
bash deploy/load-test/run-timeout-suite.sh BACKEND-ONLY-2X8 2 8 300
```

截止交卷命令示例：

```bash
JAVA_HOME=<JDK21目录> \
BUILD_RUNTIME_IMAGE=false \
LOAD_FLOW=deadline_submit \
EXAM_ID=99100004 \
bash deploy/load-test/run-timeout-suite.sh DEADLINE-SUBMIT-4X8 4 8 300
```

不得通过删除首次抖动等待、放宽 P99、减少答案大小或关闭数据库持久化来制造放行结果。

### 8.5 自动闸门解释

脚本非零退出即表示该场景不能用于放行。自动检查包括：

- k6 阈值；
- 60 秒完成数；
- 数据库 P99 和最大值；
- 重试率；
- FAILED 和遗留 PROCESSING；
- Task 的 `submission_id` 完整性；
- 主草稿和最终载荷数量；
- Session、Submission 和逻辑 Outbox 数量；
- 当前考试 Outbox 零失败；
- `node_crash` 场景实际恢复了注入时的在途任务。

纯后台场景会跳过 k6 阈值，所以即使纯后台通过，也不能替代 `status_only` 和
`deadline_submit` 两个客户端场景。

## 9. 故障注入

所有故障注入只能作用于 `exam-platform-cloud-timeout`。每轮只注入一种故障，记录数据库时间、
宿主机时间、操作对象、恢复时间和恢复结果。

### 9.1 Runtime 4 -> 3 强制退出

该场景由套件自动等待真实 `PROCESSING` 任务，再执行 `docker kill`。必须关闭同步 k6 轮询，
避免负载进程阻塞故障注入时序：

```bash
JAVA_HOME=<JDK21目录> \
BUILD_RUNTIME_IMAGE=false \
ENABLE_POLLING=false \
FAULT_INJECTION=node_crash \
FAULT_WAIT_TIMEOUT_SECONDS=20 \
EXAM_ID=99100101 \
bash deploy/load-test/run-timeout-suite.sh FAULT-RUNTIME-4-TO-3 4 8 300
```

除普通容量闸门外，还必须在 `fault-timeline.txt` 中看到：

- `processing_count_before_kill > 0`；
- 注入对象确实被 `docker kill`；
- 其余三个 Runtime 恢复执行；
- `recovered_inflight_tasks > 0`；
- 恢复任务 `attempt_count > 1`；
- 旧 claim token 没有写入第二份最终载荷；
- 当前 30 秒任务租约下最大完成时间 `<60s`。

`docker stop` 是优雅关闭，不能代替该测试；在出现 `PROCESSING` 前杀容器也不能证明租约接管。

### 9.2 Redis 短时不可用

在终端 A 启动单独的容量轮次，并将 `DUE_SECONDS` 设得足以人工操作。数据准备结束、到达真实
截止时间附近后，在终端 B 暂停 Redis，短时观察连接超时后恢复：

```bash
date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices pause redis

date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices unpause redis
```

必须验证数据库主草稿仍是最终答案来源、已经被 MySQL 接受的快照没有丢失、Redis 恢复后没有
旧版本覆盖新版本，并记录租约/队列恢复指标。Redis 故障期间新客户端接管可能按安全策略失败关闭，
不能把安全拒绝误报为数据丢失。

### 9.3 MySQL 短时连接中断

只在数据准备完全结束后注入，且必须在截止后 30 秒检查点前恢复，否则测试脚本自身的权威查询
也会失败：

```bash
date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices pause mysql

date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices unpause mysql
```

验证连接超时有界、任务回到可重试状态、恢复后由当前 token 完成、没有永久卡在 `PROCESSING`。
如果中断时间本身使 30/60 秒 SLA 不可能满足，该轮应如实判失败，不得排除故障窗口重新计算。

### 9.4 RabbitMQ 暂停与恢复

```bash
date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices pause rabbitmq

date --iso-8601=seconds
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices unpause rabbitmq
```

RabbitMQ 中断不应回滚 Runtime 本地最终事务。恢复后还要等待并验证：

- 当前考试 Outbox 最终全部 `PUBLISHED`；
- 没有 `FAILED` Outbox；
- 重复投递被 Inbox 或等价唯一约束去重；
- Grading/Reporting 最终投影数量正确；
- 已经 `GRADED` 的投影没有降级。

套件只检查逻辑 Outbox 数量和零失败，不能代替上述发布及消费端收敛检查。

### 9.5 XXL-Job 中断与恢复

为了证明调度停止，应使用隔离环境中的强制退出，并在截止后查询任务仍为 `PENDING`：

```bash
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices kill xxl-job-admin
```

记录截止后 5 秒的任务状态后恢复：

```bash
docker compose -p exam-platform-cloud-timeout \
  -f docker-compose.yml \
  -f deploy/load-test/compose.timeout-test.yaml \
  --env-file .env.microservices up -d xxl-job-admin
```

必须确认恢复后的下一次 CRON 能领取已到期任务，XXL-Job 仍保持
`SHARDING_BROADCAST + SERIAL_EXECUTION + DO_NOTHING`，且没有启用第二套 Spring 定时器。
`docker stop` 可能在优雅关闭阶段继续执行工作，不能作为“调度已停止”的唯一证据。

## 11. 数据库权威复核

每轮以结果目录中的 `database-summary.txt` 为首要证据。必要时按当前 `EXAM_ID` 手工复核：

```sql
SELECT status, COUNT(*) AS task_count,
       MIN(due_at) AS oldest_due_at,
       MAX(attempt_count) AS max_attempts
FROM submission_timeout_task
WHERE exam_id = ?
GROUP BY status;

SELECT s.status AS session_status,
       sub.status AS submission_status,
       t.status AS task_status,
       COUNT(*) AS row_count
FROM submission_timeout_task t
JOIN exam_session s ON s.id = t.session_id
LEFT JOIN submission sub ON sub.id = t.submission_id
WHERE t.exam_id = ?
GROUP BY s.status, sub.status, t.status;

SELECT COUNT(*) AS final_payloads
FROM submission_final_payload fp
JOIN submission sub ON sub.id = fp.submission_id
WHERE sub.exam_id = ?;

SELECT status, COUNT(*) AS event_count
FROM outbox_event
WHERE aggregate_type = 'SUBMISSION'
  AND aggregate_id IN (
    SELECT CAST(id AS CHAR) FROM submission WHERE exam_id = ?
  )
GROUP BY status;
```

不得用平均延迟代替 P99，不得只凭 k6 客户端状态推断数据库已经完成，也不得以 Reporting 尚未更新
否定已经完成的 Runtime 本地事务；三个时间点应分开记录。

## 12. 结果判定

### 12.1 单轮通过条件

- 命令退出码为 0；
- 10,000/10,000 在 60 秒内完成；
- DB P99 `<30s`；
- DB max `<60s`；
- 客户端场景 k6 阈值全部通过；
- `FAILED=0`、结束后 `PROCESSING=0`；
- Task、Session、Submission、主草稿、最终载荷和 Outbox 数量一致；
- 重试率在限制内；
- 没有连接池耗尽、租约错误覆盖或答案明文泄漏。

### 12.2 V2 总体放行条件

以下项目必须同时满足：

- Runtime JDK 21 全量测试通过；
- Reporting 测试通过；
- 前端状态测试和生产构建通过；
- 2 实例、4 实例的 `status_only` 与 `deadline_submit` 均通过；
- 资源分离环境的纯后台基线通过；
- Runtime 4→3、Redis、MySQL、RabbitMQ、XXL-Job 故障轮次通过；
- 告警真实送达；
- 所有 Runtime 镜像和有效配置一致；
- 无异常 FAILED、长期 PROCESSING 和 Outbox FAILED；
- 发布、回滚和审计重放流程已经演练。

任何一项缺失都保持：

```text

```

## 15. 上线和回滚演练

完整上线步骤以 `deploy/TIMEOUT_SUBMISSION_OPERATIONS.md` 为准。测试演练至少包含：

1. Runtime 兼容迁移和读写先发布，V2 保持关闭；
2. Reporting 兼容消费者发布；
3. 前端使用新增服务器时间和版本字段；
4. 暂停 XXL-Job 并等待当前执行结束；
5. 检查缺失任务为零；
6. 统一更新所有 Runtime 配置并强制重建；
7. 核对实例镜像、启动日志和有效参数；
8. 恢复 XXL-Job，先小流量观察；
9. 出现闸门异常时立即暂停作业并关闭 V2；
10. 只回退到仍能兼容读取新增表和最终载荷的版本，不删除 Flyway 新表。

不要只修改仓库中的 Nacos YAML 就认为运行时配置已经生效。需要通过 `nacos-config-init` 发布并重建
Runtime，且不得暴露 `/actuator/env` 或打印机密环境变量。

## 16. 常见误判

- 10,000 条任务最终都完成，不代表 P99 已通过；
- k6 看到交卷状态，不代表数据库 `completed_at` 已满足 SLA；
- 连接池有 96 个槽位，不代表系统支持 96 个或 10,000 个并发快照；
- 预装 10,000 份主草稿的超时测试，不代表 `/snapshot` 接口吞吐已经验证；
- `docker stop` 不等于 Runtime 崩溃或 XXL-Job 确实停止；
- Redis 故障后 MySQL 主草稿正确，不代表 Redis 租约接管体验完全正常；
- RabbitMQ 恢复后 Runtime 数据正确，不代表 Reporting 已经消费完毕；
- Testcontainers 通过，不等于资源分离容量和真实告警已经验证；
- 同机 Compose P99 不可直接外推为生产 P99；
- 修改线程数、批次或连接池后不重建 Runtime，不能证明新参数已经生效。
