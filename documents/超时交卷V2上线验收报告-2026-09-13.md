## 一、最终结论（先读这里）

**不建议、也不允许在当前状态开启主环境 V2。** 已完成项全部有证据，但存在一个**未通过的上线闸门**：
严格分片 V2 在 Runtime 4→3 强制退出下，故障分片任务的完成延迟为 71–96 秒（两轮实测
P99 75.29s/101.59s，max 75.60s/101.93s），**超过 45/60 与 30/60 两种口径的 SLA**。根因是
XXL-Job 执行器摘除延迟（注册表死亡超时约 90 秒）叠加严格分片"不跨片补领"的设计约束。
需要先解决故障接管 SLA（见 4.3 修复建议）并完成资源分离容量验收与告警送达验证后，才可重新评审。

同时，本轮验证了严格分片在故障场景下的**安全性**：零 FAILED、零遗漏、零重复最终载荷、
零重复逻辑事件、旧租约令牌未产生任何覆盖——数据一致性闸门全部通过，失败仅在延迟 SLA 维度。

## 四、严格分片 V2 的 Runtime 4→3 故障接管（本轮核心）

### 4.1 原样 node_crash 套件轮（手册 §9.1，ENABLE_POLLING=false，未执行 k6）

- 命令：`FAULT_INJECTION=node_crash FAULT_WAIT_TIMEOUT_SECONDS=20 EXAM_ID=99100101 bash deploy/load-test/run-timeout-suite.sh FAULT-RUNTIME-4-TO-3 4 8 300`
- 结果目录：`results/20260913_114531-FAULT-RUNTIME-4-TO-3`，**套件退出码 1**
- 证据：kill 时在途 8 任务（ID 全部 ≡2 mod 4，与被杀实例 shardIndex=2 一致）；+30s 与 +60s 均为
  **7500/10000**（恰为幸存 3 片的全部任务）；8 个在途任务滞留 PROCESSING；`recovered_inflight_tasks=0`。
- 套件窗口内所有轮次日志 `shardTotal=4`：故障分片在执行器摘除前**无人接管**，与严格分片设计一致。
- 套件清理自动重建第 4 实例后，同场考试**全量收敛 10000/10000**（8 个任务 attempt_count=2，经重试恢复）。

### 4.2 扩展观测轮（补充脚本 `observe-timeout-node-crash.sh`，补齐 +60s 之外的完整时间线）

两轮实测（结果目录 `20260913_120904-FAULT-OBSERVE-4-3`、`20260913_121846-FAULT-OBSERVE-4-3`）：

| 时间点 | 第 2 轮（99100103，上一轮为 99100102） |
|---|---|
| 故障注入（docker kill，在途 8 任务被遗弃） | 12:22:38 |
| 幸存 3 片完成各自任务后停滞 | 12:23:00（8196 done，1796 PENDING + 8 遗弃） |
| 执行器注册 4→3（xxl_job_registry 采样） | 12:23:24→12:23:48 之间（kill+46~70s） |
| 首次 `shardTotal=3` 触发并领取故障分片 | 12:23:49（单轮 claimed=602） |
| 遗弃在途任务经租约过期+重试恢复 | `recovered_inflight_tasks=8`（attempt_count=2 ×8） |
| 全部完成 | 12:23:51（**距 kill 71 秒**；第 1 轮为 96 秒） |

最终态一致性（两轮均通过）：done=10000、FAILED=0、遗留 PROCESSING=0、最终载荷=10000 且
`max_payload_per_submission=1`、逻辑事件=10000、Outbox FAILED=0——**旧令牌未产生任何重复覆盖**。

延迟（due_at→completed_at）：第 2 轮 P50 15.5s / P90 73.7s / **P99 75.29s / max 75.60s**；
第 1 轮 P99 101.59s / max 101.93s。

### 4.3 判定与修复建议

- **一致性/安全性：PASS**；**接管 SLA：FAIL（71–96s > 60s）**。这是严格分片相对旧全局任务池的真实代价：
  接管时间由 XXL-Job 执行器摘除节奏决定（注册死亡超时 = 3×30s 心跳 ≈ 90s），而非 30s 租约。
- 修复建议（需单独评审，本次未改动业务代码）：
  1. 缩短执行器摘除窗口：调小 xxl-job-admin 注册死亡超时（现为 `BEAT_TIMEOUT×3=90s` 硬编码）或缩短心跳；
  2. 或在协调器增加"分片无存活执行器"的对账接管（需防止拓扑误判，属业务变更）；
  3. 或修订 SLA 口径：故障场景按"kill+90s 执行器摘除 + 租约过期"另行设定（需业务确认）。

## 六、运维演练（隔离环境，全部真实执行）

- **发布演练**（`results/20260913_144439-OPS-RELEASE`）：停止调度→排空在途（PROCESSING=0）→重建
  Runtime 至 2 实例→启动日志与执行器注册（90s 摘除窗口内出现 2 条打向旧地址的 500 触发，符合预期）→
  恢复调度→发布后验证轮 100/100 收敛、`shardTotal=2` 与实例数一致。
  勘误记录：首次执行将 `xxl_job_info.trigger_status`（1=运行/0=停止）语义用反，已在日志中勘误并
  以正确语义闭环；该教训不影响演练结论。
- **回滚演练**（`results/…-OPS-ROLLBACK`）：停止→排空→切换 `timeout-rollback:20260913`
  （HEAD+启动修复，无分片代码）→重建→恢复→60/60 收敛，窗口内 **0 条** `shardTotal=` 日志证实旧
  全局任务池代码真实运行；随后回滚前进至当前镜像并验证 `mode=V2` 初始化日志。
  注：HEAD 提交本身不可启动（双构造缺陷），回滚目标必须至少包含两处 `@Autowired` 修复——
  **建议尽快提交这两处修复**，否则任何环境的回滚基线都是坏的。
- **受控审计重放演练**（`results/…-OPS-REPLAY`）：F-08 尝试封顶现场（FAILED + `LEASE_ATTEMPTS_EXHAUSTED`
  + Session=SUBMISSION_FAILED + 零载荷，经预置 attempt_count=maxAttempts 快速构造）→ ADMIN 令牌调用
  `POST /api/v1/exams/{examId}/timeout-submissions/{taskId}/replay` → HTTP 200，`replayCount=1` →
  任务经重放队列恢复并由调度最终化：DONE + SUBMITTED + 恰好 1 载荷 + 1 逻辑事件；
  **重复重放被拒绝**（状态不允许，replay_count 不变）；学生令牌在方法级安全被拒绝（`@PreAuthorize`
  生效，无状态变化；错误码映射为 500 而非 403，记为次要 API 映射问题）；`outbox_event` 出现
  `AUDIT/AuditOperationRecorded` 审计事件（含被拒绝的调用）。
- 观察项（非缺陷）：删除数据库主草稿与 Redis 快照后，超时最终化以空草稿完成交卷（`loadDraft(null)`
  返回 `SnapshotDraft.empty()`）——"空卷也固化交卷状态"的设计语义，与 F-15 申诉证据保留并不冲突，
  已如实记录。
